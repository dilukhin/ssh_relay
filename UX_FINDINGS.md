# Состояние quoting- и UX-задач ssh_relay

Дата актуализации: 2026-07-31.

Документ фиксирует подтверждённые проблемы эксплуатации `ssh_relay`, их состояние в версии `0.6.0` и оставшиеся работы. Исходные наблюдения получены при работе из Windows PowerShell 5.1 с версией 0.5.1.

## Обозначения

- **Выполнено** — требование реализовано и покрыто доступной проверкой.
- **Частично** — существенная часть проблемы устранена, но исходный сценарий закрыт не полностью.
- **Не выполнено** — требуемого интерфейса или проверки в версии 0.6.0 нет.

## Что закрыто версией 0.6.0

### Машинный результат `exec` и `sudo-exec`

Режим `--json` возвращает один JSON-объект со следующими группами данных:

- идентичность relay и активной сессии;
- `transaction_id` и источник идентификатора;
- безопасные `change_target` и `change_description`;
- `command_status` и точный `command_exit_code`;
- `receipt_status`, `receipt_id` и hash;
- `partial_success`;
- удалённые stdout/stderr;
- стабильные поля ошибки и стадия сбоя.

Машинные коды процесса:

| Код | Значение |
|---:|---|
| `0` | операция успешна |
| `10` | команда достоверно не запускалась |
| `11` | удалённая команда завершилась с ненулевым кодом |
| `12` | команда успешна, receipt не подтверждён |
| `13` | результат удалённой команды неизвестен |
| `2` | синтаксическая ошибка CLI до формирования JSON |

### Безопасный risky receipt

Версия 0.6.0:

- не записывает полный текст команды;
- хранит SHA-256 точной пользовательской команды;
- создаёт `transaction_id` и `receipt_id`;
- хранит `previous_receipt_hash` и self-hash записи;
- проверяет последнюю запись перед запуском изменяющей команды;
- блокирует повторный уже записанный `transaction_id`;
- применяет `umask 077` и режим `0600`;
- отклоняет конечный путь, являющийся символической ссылкой;
- повторно читает добавленную строку и проверяет её идентификатор и hash.

Hash-цепочка не является цифровой подписью и не защищает от владельца файла, который может пересчитать весь журнал.

### Неопределённые результаты

После возможной отправки запроса или запуска удалённой команды relay действует консервативно:

- потеря ответа daemon не удаляет session-файл автоматически;
- timeout после запуска команды возвращает `unknown`;
- превышение лимита вывода после запуска команды возвращает `unknown`;
- успешная команда с неподтверждённым receipt возвращает `partial_success`.

## Основная незакрытая проблема: quoting

Текущая цепочка остаётся такой:

```text
локальный shell -> argv Python -> argparse -> JSON IPC -> удалённый shell
```

Если сложная команда передаётся позиционным аргументом, PowerShell или `cmd.exe` могут обработать кавычки и специальные символы ещё до запуска Python. Relay не может восстановить потерянные границы аргументов.

### Требуемое решение

Для `exec` и `sudo-exec` нужны взаимоисключающие способы ввода:

```text
--command-file PATH
--command-stdin
```

Требования:

- содержимое файла читает CLI как UTF-8;
- stdin читается до EOF;
- применяется отдельный небольшой лимит размера;
- пустая команда отклоняется локально;
- конфликт позиционного аргумента, файла и stdin завершается кодом `2`;
- содержимое передаётся daemon отдельным JSON-полем;
- интерактивный stdin по-прежнему не поддерживается;
- текст команды не печатается в диагностике;
- `command_hash` вычисляется от фактически переданных UTF-8 байтов.

`argparse.REMAINDER` не считается достаточным решением: локальный shell всё равно обрабатывает часть синтаксиса до Python.

## Рекомендуемые последующие задачи

### P1. Непрозрачный ввод команды

Реализовать `--command-file` и `--command-stdin`, затем проверить побайтовую эквивалентность содержимого на стороне daemon.

### P1. Диагностика распавшегося argv

Сообщение должно безопасно указывать:

- что CLI получил несколько аргументов вместо одной удалённой команды;
- что команда не отправлялась daemon;
- количество лишних аргументов без вывода их содержимого;
- рекомендуемый способ файлового или stdin-ввода.

### P1. JSON для read-only команд

Рассмотреть стабильный JSON-контракт для:

- `status`;
- `list`;
- будущего `inspect`.

Токены, пароли, приватные ключи и содержимое session-файлов в результат не включать.

### P1. Verify и выполнение скрипта

Необходимо отдельно спроектировать:

- `inspect --json`;
- `exec-script` и `sudo-exec-script`;
- ограничение размера;
- явный shell из ограниченного списка;
- закрытый интерактивный stdin;
- hash переданных байтов;
- cleanup временного файла, если он используется.

Verify, rollback, expected state и классификация риска остаются ответственностью `agent-safe`. Relay может предоставить безопасный транспорт и машинный результат, но не должен переносить к себе политику транзакций.

### P1. Регрессия upload

Минимальная матрица:

- CLI и daemon запущены из разных каталогов;
- detached daemon;
- overwrite файла тем же размером, но другим содержимым;
- сравнение SHA-256;
- Windows-style и POSIX remote path;
- отказ без `--overwrite`;
- превышение лимита;
- timeout;
- отсутствие временного файла после ошибки.

### P2. UTF-8 и версия

- настроить UTF-8 для локального вывода Windows с безопасным fallback;
- добавить тест согласованности `__version__`, `--version` и README.

## Регрессионная матрица quoting

Проверять PowerShell 5.1, PowerShell 7, `cmd.exe` и POSIX shell.

Fixtures:

- ASCII и кириллица;
- одинарные и двойные кавычки;
- пробелы и переводы строк;
- `$()`, `$env:VAR`, `%VAR%`;
- `|`, `;`, `&&`, `>`, `2>&1`;
- JSON и регулярные выражения;
- inline Python и `awk`;
- аргументы, начинающиеся с `-` и `--`;
- пустой stdout, непустой stderr и ненулевой exit code;
- timeout и превышение лимита вывода.

## Критерий закрытия документа

Все findings можно считать закрытыми только после того, как:

1. сложная команда из файла или stdin без изменений доходит до daemon во всех поддерживаемых shell;
2. ошибка однозначно указывает стадию;
3. read-only команды имеют достаточный машинный интерфейс;
4. upload защищён автоматической регрессией;
5. UTF-8 проверен на PowerShell 5.1;
6. результаты расширенной приёмки Issue #2 подтверждены на реальном сервере.
