# Проблемы quoting и эксплуатации ssh_relay

## Цель

Документ собирает подтверждённые затруднения при работе с `ssh_relay` из Windows PowerShell 5.1 и предлагает доработки, которые сокращают число повторных запусков, ложных диагностик и неоднозначных результатов.

Основные источники:

* рабочая сессия 20 июля 2026 года с `ssh_relay` 0.5.1 и Linux-сервером;
* каноническая память OpenCode и отчёт `knowledge-base/ssh-relay/issues-and-improvements.md` от 14 июля 2026 года;
* текущая реализация и README репозитория `ssh_relay`.

История других диалогов напрямую недоступна. Вместо неё использованы подтверждённые факты, ранее перенесённые в каноническую память.

## Краткий итог

Главный источник потерь времени - передача сложной удалённой команды как одного позиционного аргумента:

```text
PowerShell 5.1 -> argv Python -> argparse ssh_relay -> JSON IPC -> удалённый shell
```

Если команда содержит inline Python, `awk`, JSON или регулярное выражение, добавляется ещё один уровень синтаксиса. Relay сохраняет строку, которую уже получил Python, но не может восстановить кавычки и границы, потерянные локальным PowerShell. Пользователь при этом видит ошибку `неизвестные аргументы` от `argparse`, а не объяснение реальной причины.

За одну проверку стенда две простые проверки пришлось повторять несколько раз только из-за quoting. Это не повредило сервер, но замедлило диагностику и сначала привело к недостаточно обоснованному выводу о состоянии `parser.json`.

## Подтверждённые случаи

### UX-1. Удалённая команда распадается на локальные аргументы

**Приоритет:** P0.

В текущей сессии команды с вложенными кавычками для `grep`, `awk` и `python3 -c` несколько раз завершились до обращения к daemon:

```text
ssh_relay.py: ошибка: неизвестные аргументы: ...
```

Примеры содержали:

* поиск JSON-поля с чередованием одинарных и двойных кавычек;
* inline Python со строковыми литералами;
* `awk` с блоками, `$0` и печатью маркеров;
* регулярные выражения с пробелами и квадратными скобками.

Подтверждённый ранее более опасный вариант: основная risky-команда выполнилась, а verify-команда с `$()` и вложенными кавычками распалась локально. Это вызвало Recovery Mode, хотя удалённое состояние оказалось ожидаемым.

**Корневая причина:** `exec` и `sudo-exec` принимают только `remote_command` как один позиционный аргумент. Непрозрачного ввода команды из файла или stdin нет. До запуска `ssh_relay.py` строку разбирает вызывающий shell.

**Временный обход:** использовать несколько коротких команд без `$()`, inline JSON и вложенных языков. Сложный скрипт передавать отдельным файлом и запускать простой командой.

### UX-2. Диагностика указывает не на тот слой

**Приоритет:** P1.

Сообщение `неизвестные аргументы` корректно для `argparse`, но не объясняет, что предполагаемая одна удалённая команда дошла как несколько локальных аргументов. Пользователь начинает исправлять удалённый `bash`, хотя команда ещё не была отправлена в daemon.

Нет стабильного признака стадии сбоя:

* локальный shell;
* разбор CLI;
* соединение с daemon;
* SSH transport;
* удалённый shell;
* удалённая программа.

### UX-3. Inline-команды с несколькими языками непропорционально дороги

**Приоритет:** P1.

Попытка безопасно прочитать JSON через `python3 -c` потребовала согласовать синтаксис PowerShell, Python CLI, удалённого shell и самого Python-кода. Попытка проверить секцию INI через `awk` добавила правила `$0`, фигурных скобок и строковых литералов.

После двух ошибок тот же результат был получен простыми командами `grep` и `python3 -m json.tool`. Это рабочий обход, но он переносит сложность на оператора и увеличивает число сетевых вызовов.

### UX-4. UTF-8 в PowerShell 5.1 требует внешнего префикса

**Приоритет:** P1.

Для устойчивого русского вывода перед каждым вызовом использовалось:

```powershell
$env:PYTHONIOENCODING = 'utf-8'
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

Без этого локализованные сообщения Python и native-команд могут отображаться как кракозябры. В `ssh_relay.py` нет явной настройки `sys.stdout` и `sys.stderr` через `reconfigure(encoding="utf-8")`.

### UX-5. Нет машинного формата результата

**Приоритет:** P1.

Проверки строятся на человекочитаемом выводе и дополнительных маркерах вида `KEY=VALUE`. Комбинированная команда может вывести только часть ожидаемых строк, а вызывающая сторона должна самостоятельно различить:

* код удалённой команды;
* ошибку relay;
* отсутствие совпадений `grep`;
* пустой штатный вывод;
* обрезанный вывод;
* timeout.

Для `status`, `list`, `exec` и `sudo-exec` нужен JSON-контракт со стабильными именами полей.

### UX-6. Verify и risky receipt усиливают проблему quoting

**Приоритет:** P1.

`safe` и `ssh_relay` могут повторно оборачивать строки change, rollback и verify. Чем больше уровней shell-команд, тем выше вероятность, что изменение выполнится, а проверка не дойдёт до сервера.

Receipt сейчас сохраняет полную команду. Это полезно для расследования, но небезопасно, если в командной строке случайно оказался секрет.

### UX-7. Историческая проблема upload исправлена, но требует регрессии

**Приоритет:** P1 для тестов, исправление уже есть в 0.5.1.

В рабочей цепочке команда `upload` не изменила удалённый файл, хотя повторная проверка размера не сразу показала причину. Корневая причина конкретного эпизода не была доказана. Отдельно подтверждено, что коммит `8059f8a` исправил известный класс проблем протокола: файл теперь читается CLI-процессом и передаётся daemon как содержимое, а Windows-style пути нормализуются для SFTP.

Риск возврата остаётся, потому что автоматизированных тестов нет. Нужны проверки daemon в другом рабочем каталоге, detached daemon, совпадающего размера старого и нового файла, overwrite и контрольной суммы после передачи.

### UX-8. Документация версии отстаёт от кода

**Приоритет:** P2.

До данной документационной правки в `ssh_relay.py` была указана версия 0.5.1, а README сообщал 0.5.0 как текущую и ожидаемую. Это затрудняло понимание, содержит ли используемый relay исправление `upload`.

### UX-9. Ошибки удалённой команды легко принять за ошибку relay

**Приоритет:** P2.

В текущей сессии `printf '---\n'` на удалённом сервере интерпретировал строку с дефисами как опцию. Это не дефект relay и не quoting-сбой: команда дошла и завершилась ошибкой уже в удалённой программе.

Аналогично `pgrep -af` совпал с собственной диагностической командой. Это ожидаемое поведение инструмента, но без структурированного результата такие случаи увеличивают время анализа.

Relay должен явно показывать стадию и exit code, чтобы подобные ошибки не смешивались с транспортными.

## Предлагаемые доработки

### P0. Непрозрачная передача команды

Добавить взаимоисключающие способы ввода для `exec` и `sudo-exec`:

```text
--command-file PATH
--command-stdin
```

Требования:

* файл читается CLI как UTF-8 без локального shell parsing содержимого;
* stdin читается до EOF с документированным лимитом;
* в IPC команда остаётся отдельным JSON-полем;
* daemon получает строку побайтно эквивалентно после UTF-8 decode;
* позиционный `remote_command` сохраняется для простых случаев;
* пустая команда и конфликт режимов завершаются понятной локальной ошибкой.

`argparse.REMAINDER` не решает проблему полностью: PowerShell всё равно успевает обработать кавычки, `$()` и специальные символы до Python.

### P1. Объяснение ошибки argv

Переопределить обработку лишних аргументов для `exec` и `sudo-exec`. Сообщение должно указывать:

* что relay получил несколько argv вместо одной команды;
* что команда не отправлялась на сервер;
* рекомендацию использовать `--command-file` или `--command-stdin`;
* безопасное количество аргументов без вывода их содержимого.

Отладочный режим `--debug-argv` допустим только с редактированием потенциальных секретов.

### P1. JSON-результат и стадия ошибки

Добавить `--json` со стабильной схемой:

```json
{
  "ok": false,
  "stage": "local_cli",
  "session": "default",
  "target": "user@example:22",
  "transport_ok": false,
  "remote_exit_code": null,
  "stdout": "",
  "stderr": "",
  "stdout_encoding": "utf-8",
  "truncated": false,
  "duration_ms": 0,
  "error_code": "REMOTE_COMMAND_SPLIT"
}
```

Значения `stage`: `local_cli`, `local_daemon`, `ssh_transport`, `remote_shell`, `remote_process`, `receipt`, `verify`.

### P1. UTF-8 по умолчанию

На Windows попытаться выполнить:

```python
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
sys.stderr.reconfigure(encoding="utf-8", errors="replace")
```

JSON-режим всегда должен использовать UTF-8 и не зависеть от локализованного текста.

### P1. Verify как операция первого класса

Добавить `--verify-command-file` и выполнять change и verify раздельно. Результат и receipt должны содержать два независимых exit code. Ошибка доставки verify должна отличаться от verify mismatch.

Для интеграции с `safe` добавить явный режим `exec|sudo-exec`, чтобы не вкладывать один универсальный shell-вызов в другой.

### P1. Безопасная политика receipt

Добавить:

```text
--receipt-command-policy hash|redacted|full
```

Значение по умолчанию - `redacted`. Receipt должен хранить hash команды, описание цели, результат change и verify. Полный текст разрешать только явно.

### P1. Автоматизированные тесты upload

Минимальные сценарии:

* CLI и daemon запущены из разных каталогов;
* detached daemon;
* overwrite файла тем же размером, но другим содержимым;
* проверка SHA-256 локального и удалённого файла;
* POSIX и Windows-style удалённые пути;
* отказ без `--overwrite`;
* превышение лимита и timeout;
* отсутствие временного файла после ошибки.

### P2. Синхронизация версии

Версия в коде, README и выводе `status` должна проверяться одним тестом или обновляться из одного источника.

## Регрессионная матрица quoting

Проверять PowerShell 5.1, PowerShell 7, `cmd.exe` и POSIX shell. Для каждого окружения команда на стороне daemon должна совпадать с fixture.

Fixtures:

* ASCII и кириллица;
* одинарные и двойные кавычки;
* пробелы и переводы строк;
* `$()`, `$env:VAR`, `%VAR%`;
* `|`, `;`, `&&`, `>`, `2>&1`;
* JSON и регулярные выражения;
* inline Python и `awk`;
* аргументы, начинающиеся с `-` и `--`;
* пустой stdout, непустой stderr и ненулевой exit code;
* timeout и превышение лимита вывода.

## Рекомендуемый порядок

1. Реализовать `--command-file` и `--command-stdin`.
2. Добавить диагностику разделённого argv и тесты PowerShell 5.1.
3. Добавить JSON-контракт и явную стадию ошибки.
4. Сделать verify операцией первого класса и согласовать интеграцию с `safe`.
5. Изменить политику receipt.
6. Зафиксировать upload интеграционными тестами.
7. Включить UTF-8 по умолчанию и синхронизацию версии.

## Критерий результата

Работа считается улучшенной, если сложная команда из файла или stdin без изменений доходит до daemon во всех поддерживаемых shell, а любая ошибка однозначно указывает стадию. Для типовой диагностики JSON и INI не должно требоваться повторять вызов из-за локального quoting.
