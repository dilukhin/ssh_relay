# SSH Relay

Используй `ssh_relay` только через уже запущенный пользователем relay. Не запускай прямой `ssh` и не запрашивай SSH-, sudo-пароли, passphrase ключей или другие секреты.

## Перед работой

1. Проверь нужную сессию: `py ssh_relay.py status --name <session>`.
2. При необходимости посмотри сессии: `py ssh_relay.py list`.
3. Для короткой диагностики используй `exec`, например: `py ssh_relay.py exec --name <session> "hostname && whoami && pwd"`.

Если `status` показывает восстановление SSH, не запускай рабочую команду повторно. Дождись восстановления и проверь состояние ещё раз.

## Короткие команды

`exec` предназначен только для коротких неинтерактивных команд с ограниченным выводом:

```text
py ssh_relay.py exec --name <session> "<command>"
```

Для короткой root-команды допустим `sudo-exec`, только если daemon запущен с `--enable-sudo`:

```text
py ssh_relay.py sudo-exec --name <session> "<command>"
```

Не запускай через них сборки, долгие тесты, интерактивные программы, команды с запросом пароля или потенциально большим выводом.

## Длительные процессы

Для сборок, CTest, интеграционных тестов и других длительных неинтерактивных процессов используй `job`:

```text
py ssh_relay.py job start --name <session> --job <job> "<command>"
py ssh_relay.py job status --name <session> --job <job>
py ssh_relay.py job tail --name <session> --job <job>
py ssh_relay.py job wait --name <session> --job <job>
py ssh_relay.py job stop --name <session> --job <job>
py ssh_relay.py job list --name <session>
```

`job start` подтверждает только запуск механизма job. Итог длительной команды определяется последующим `job status`/`job wait` и `exit_code`.

Ключевое правило: **таймаут или обрыв управляющего транспорта не означает завершение или ошибку удалённого процесса**. Если результат `job start` неизвестен, не повторяй исходный запуск. После восстановления relay сначала выполни `job status --job <job>` или `job list` и установи судьбу первой задачи.

`job wait` локально опрашивает короткий `job status`; истечение его локального timeout не останавливает удалённую задачу. Продолжай проверять её по тому же имени job.

`job tail` используй вместо чтения полного журнала. Не запрашивай большие логи целиком.
Не запускай через `job` команды, которые сами создают новую session/process group или daemonize с выходом из группы job: такой процесс relay не сможет надёжно контролировать.

## Остановка

Обычный `job stop` сначала отправляет мягкое завершение группе процессов. `--force` применяй только отдельным осознанным шагом, если мягкая остановка не сработала.

## `--risky` и agent-safe

Для коротких изменяющих команд сохраняется существующий контракт:

```text
py ssh_relay.py exec --name <session> --risky "<command>"
```

Успешный `job start` не равен успешному завершению рискованной операции, поэтому обычный финальный receipt agent-safe при старте job не создаётся. На текущем этапе long-job lifecycle receipts `started/completed/failed` не поддерживаются; не имитируй их несовместимым форматом.

## Безопасность

Не передавай секреты в задания модели, логи, receipts и диагностический вывод. Не добавляй SSH- или sudo-пароли в команды. Не публикуй session-файлы и токены relay. Не ослабляй проверку host key.
