# Findings: интеграция ssh_relay 0.5.1 с agent-safe

Дата наблюдения: 2026-07-23.

Примечание: историческое имя ветки содержит `android-termux`, однако этот документ описывает интеграцию `ssh_relay` с `agent-safe` при работе с удалёнными Linux/VPS. Android и Termux в данном исследовании не проверялись.

## Контекст

Через именованные relay-сессии выполнялась настройка SSH-доступа на трёх VPS. Требовалось добавить ограниченный публичный ключ пользователю `tunneluser`, сохранив существующие ключи, права и удалённые receipts.

Сессии работали в режиме `--enable-sudo`, потому что целевой `authorized_keys` принадлежал другому пользователю.

## Что сработало

- `status --name` подтвердил доступность каждой именованной сессии;
- `exec --name "hostname && whoami && pwd"` позволил установить идентичность хоста и контекст;
- `sudo-exec --risky --receipt-path /var/lib/agent-safe/changes.jsonl` выполнил изменение и оставил receipt на целевом сервере;
- stdout, stderr и exit code были пригодны для внешней проверки;
- отдельный verify через `sudo-exec` подтвердил точную строку ключа, владельца и режим `600`;
- изменение выполнялось отдельно для каждого хоста, поэтому сбой одного сервера не создавал неопределённое состояние остальных.

## Подтверждённые ограничения интеграции

### 1. Адаптер agent-safe не поддерживает `sudo-exec`

Интерфейс `safe ssh-relay-risky` ожидает relay-команду вида:

```text
<relay> exec --name <name> ...
```

Для изменения файла, доступного только root, обычный `exec` недостаточен. `sudo -n` также не работал, потому что daemon был запущен с сохранённым в памяти sudo-паролем, а не с ограниченным `NOPASSWD`.

В результате пришлось использовать generic `safe exec-risky`, оборачивая локальный вызов:

```text
py ssh_relay.py sudo-exec --name <name> --risky ...
```

Это сохраняет базовый протокол, но теряет часть семантики специализированного relay-adapter.

### 2. Receipt существует на двух уровнях

В рабочем вызове участвовали:

- локальный receipt транзакции `safe`;
- удалённый JSONL receipt, записанный `ssh_relay --risky`.

Это правильная модель, но связь между receipts не формализована. Локальная транзакция не хранит идентификатор удалённой записи, а удалённая запись не знает локальный transaction ID.

### 3. Составная удалённая команда классифицируется как unknown

Идемпотентное добавление ключа требовало нескольких шагов:

- проверить отсутствие строки;
- при необходимости добавить её;
- восстановить owner и mode.

Для удалённого shell это одна логическая транзакция, но локальный risk classifier увидел `||` и `;` и отметил команду как unknown/non-atomic. Команда при этом была детерминированной, имела точный target, rollback и verify.

Запрещать любые shell-цепочки нельзя: атомарный helper на удалённой стороне не всегда существует. Нужен способ передавать проверенный скрипт или manifest операции как единое содержимое с hash.

### 4. Rollback и verify на Windows чувствительны к quoting

Надёжным оказался подход с файлами:

```text
--expected-state-file
--rollback-command-file
--verify-command-file
```

Inline JSON и verify с `$()` или несколькими уровнями кавычек в PowerShell 5.1 создают риск неверного разделения аргументов. Простые удалённые команды с pipeline работали предсказуемее, чем shell substitution.

### 5. Проверка target требует отдельного discovery

Пользователь сначала указал неверное имя учётной записи. Read-only `getent passwd` и `id` предотвратили изменение несуществующего пользователя. Для production-операций relay-adapter должен поощрять обязательную фиксацию:

- hostname;
- SSH-пользователя relay;
- cwd;
- целевого пользователя и home;
- режима sudo;
- фактического target path.

### 6. Удалённый receipt сохраняет полную команду

Текущая risky-запись включает поле `command` без автоматического удаления секретов. Если в команде окажется токен, пароль, приватный URL или другой чувствительный аргумент, он попадёт в JSONL receipt.

Для безопасной эксплуатации receipt должен по умолчанию хранить:

- hash команды или скрипта;
- безопасное описание операции;
- точный target;
- режим sudo;
- exit code;
- идентификаторы локальной и удалённой транзакций.

Полную команду допустимо сохранять только явно и после предупреждения о риске утечки секретов.

### 7. Команда может выполниться, а receipt — не записаться

Сейчас удалённая команда выполняется первой. Receipt записывается только после её успешного завершения. Если запись receipt завершается ошибкой, состояние удалённого хоста уже изменено.

Такой результат нельзя представлять как обычную ошибку выполнения. Нужен отдельный машинно различимый исход:

```json
{
  "command_status": "succeeded",
  "receipt_status": "failed",
  "partial_success": true
}
```

Оператор и `agent-safe` должны понимать, что rollback или ручная проверка требуются из-за потери аудита, а не из-за невыполненной команды.

### 8. Целостность и корреляция receipts не защищены

Один `receipt_id` или hash записи позволит связать локальную и удалённую транзакции, но не обнаружит удаление или перестановку строк журнала.

Минимально полезная схема:

- `transaction_id`;
- `receipt_id`;
- `previous_receipt_hash`;
- `receipt_hash`;
- устойчивый идентификатор удалённого хоста;
- timestamp UTC.

Полноценная криптографическая подпись для простого relay может быть избыточна, но цепочка hash повысит обнаруживаемость подмены журнала.

## Рекомендуемые доработки ssh_relay

### P0. Машиночитаемый результат risky-операции

После `exec --risky` и `sudo-exec --risky` CLI должен уметь опционально печатать JSON с полями:

- session name;
- remote host label;
- command exit code;
- command status;
- receipt status;
- partial success;
- receipt path;
- receipt ID и hash записи;
- transaction ID, если он передан вызывающей стороной;
- sudo mode;
- timestamp.

Это позволит `agent-safe` надёжно связать локальную и удалённую транзакции и отличить ошибку команды от ошибки аудита.

### P0. Безопасный формат risky receipt

Нужно исключить автоматическое сохранение полной команды с потенциальными секретами. Предпочтительный формат должен хранить hash команды или скрипта и безопасные метаданные операции.

### P1. Команда выполнения проверенного скрипта

Вместо сложной inline-команды полезен режим, принимающий локальный обычный файл ограниченного размера:

```text
ssh_relay exec-script --name NAME script.sh
ssh_relay sudo-exec-script --name NAME --risky script.sh
```

Требования:

- содержимое передаётся daemon, а не читается из его cwd;
- hash скрипта включается в receipt;
- shell выбирается явно из ограниченного списка;
- stdin остаётся закрытым для интерактивного ввода;
- действуют существующие timeout и output limit;
- команда не превращается в произвольную рекурсивную передачу каталогов;
- размер скрипта ограничен отдельным безопасным лимитом.

### P1. Discovery-команда для контекста

Опциональная команда наподобие `inspect --name NAME --json` могла бы вернуть безопасный JSON:

- host/port/user из активной сессии;
- hostname удалённого узла;
- remote cwd;
- включён ли sudo;
- версию relay;
- fingerprint host key или другой устойчивый идентификатор узла.

Она не должна выводить token, пароль, ключ или содержимое session-файла.

## Рекомендуемые доработки agent-safe adapter

Специализированный adapter должен поддерживать режим:

```text
safe ssh-relay-risky --relay-mode exec
safe ssh-relay-risky --relay-mode sudo-exec
```

Для `sudo-exec` adapter должен:

- требовать системный receipt path;
- включать режим sudo в expected state;
- выполнять verify тем же режимом, если обычный SSH-пользователь не читает target;
- передавать локальный transaction ID в `ssh_relay`;
- связывать локальный transaction ID с remote receipt ID;
- различать command failure, receipt failure и partial success;
- не советовать `sudo -n`, если relay использует собственный `sudo-exec`.

Классификацию shell-цепочек, expected state, rollback и verify следует дорабатывать в `agent-safe`, а не переносить в основной протокол relay.

## Разделение ответственности

| Изменение | Проект |
|---|---|
| JSON-результат risky-операции | `ssh_relay` |
| Receipt ID, transaction ID и hash | `ssh_relay` |
| Partial success при ошибке receipt | `ssh_relay` |
| Безопасное редактирование команды в receipt | `ssh_relay` |
| `inspect --json` | `ssh_relay` |
| `exec-script` и `sudo-exec-script` | `ssh_relay` |
| Поддержка `sudo-exec` в специализированном adapter | `agent-safe` |
| Классификация составных shell-команд | `agent-safe` |
| Expected state, rollback и verify files | `agent-safe` |
| Связь локальной транзакции с удалённым receipt | оба проекта |

## Критерии интеграционного теста

1. Запустить daemon с `--enable-sudo`.
2. Через `safe` создать root-owned тестовый файл командой `sudo-exec --risky`.
3. Подтвердить локальный receipt и удалённый JSONL receipt.
4. Проверить наличие transaction ID, receipt ID и hash.
5. Проверить owner/mode через sudo verify.
6. Выполнить rollback и подтвердить состояние.
7. Смоделировать ошибку записи receipt и подтвердить машинный результат `partial_success`.
8. Убедиться, что token, SSH-пароль, sudo-пароль и тестовые секреты отсутствуют во всех выводах и receipts.
9. Повторить сценарий с именованными сессиями на двух хостах и доказать отсутствие cross-session target mix-up.
10. Проверить сценарий со скриптом ограниченного размера без интерактивного stdin.

## Приоритет реализации

### P0

1. Машиночитаемый JSON-результат risky-операции.
2. `transaction_id`, `receipt_id` и hash.
3. Отдельное состояние partial success при ошибке записи receipt.
4. Исключение секретов из risky receipt.
5. Поддержка `sudo-exec` в адаптере `agent-safe`.

### P1

1. `inspect --json`.
2. `exec-script` и `sudo-exec-script` с hash, лимитом размера и явным shell.
3. Интеграционный тест с двумя именованными сессиями.

## Операционный вывод

До появления поддержки `sudo-exec` в специализированном adapter допустим generic `safe exec-risky` вокруг `ssh_relay sudo-exec --risky`, если явно заданы target, expected state, rollback, verify и удалённый receipt.

Inline JSON и сложные verify-команды в PowerShell следует заменять файлами. Команды с секретами нельзя передавать через `--risky`, пока receipt сохраняет полную команду без редактирования.
