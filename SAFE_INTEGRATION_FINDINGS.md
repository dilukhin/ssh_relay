# Findings: интеграция ssh_relay с agent-safe

Дата наблюдения: 2026-07-23.

## Контекст

Через именованные relay-сессии выполнялась настройка SSH-доступа на трёх VPS. Требовалось добавить ограниченный публичный ключ пользователю `tunneluser`, сохранив существующие ключи, права и удалённые receipts.

Сессии работали в режиме `--enable-sudo`, потому что целевой `authorized_keys` принадлежал другому пользователю.

## Что сработало

- `status --name` подтвердил доступность каждой именованной сессии;
- `exec --name "hostname && whoami && pwd"` позволил установить идентичность хоста и контекст;
- `sudo-exec --risky --receipt-path /var/lib/agent-safe/changes.jsonl` выполнил изменение и оставил receipt на целевом сервере;
- stdout, stderr и exit code были пригодны для внешней проверки;
- отдельный verify через `sudo-exec` подтвердил точную строку ключа, владельца и режим `600`;
- изменение выполнялось отдельно для каждого хоста, поэтому сбой одного сервера не создавал неопределённое состояние остальных.

## Подтверждённые ограничения интеграции

### 1. Адаптер agent-safe не поддерживает `sudo-exec`

Интерфейс `safe ssh-relay-risky` ожидает relay-команду вида:

```text
<relay> exec --name <name> ...
```

Для изменения файла, доступного только root, обычный `exec` недостаточен. `sudo -n` также не работал, потому что daemon был запущен с сохранённым в памяти sudo-паролем, а не с ограниченным `NOPASSWD`.

В результате пришлось использовать generic `safe exec-risky`, оборачивая локальный вызов:

```text
py ssh_relay.py sudo-exec --name <name> --risky ...
```

Это сохраняет базовый протокол, но теряет часть семантики специализированного relay-adapter.

### 2. Receipt существует на двух уровнях

В рабочем вызове участвовали:

- локальный receipt транзакции `safe`;
- удалённый JSONL receipt, записанный `ssh_relay --risky`.

Это правильная модель, но связь между receipt не формализована. Локальная транзакция не хранит идентификатор удалённой записи, а удалённая запись не знает локальный transaction ID.

### 3. Составная удалённая команда классифицируется как unknown

Идемпотентное добавление ключа требовало нескольких шагов:

- проверить отсутствие строки;
- при необходимости добавить её;
- восстановить owner и mode.

Для удалённого shell это одна логическая транзакция, но локальный risk classifier увидел `||` и `;` и отметил команду как unknown/non-atomic. Команда при этом была детерминированной, имела точный target, rollback и verify.

Запрещать любые shell-цепочки нельзя: атомарный helper на удалённой стороне не всегда существует. Нужен способ передавать проверенный скрипт или manifest операции как единое содержимое с hash.

### 4. Rollback и verify на Windows чувствительны к quoting

Надёжным оказался подход с файлами:

```text
--expected-state-file
--rollback-command-file
--verify-command-file
```

Inline JSON и verify с `$()` или несколькими уровнями кавычек в PowerShell 5.1 создают риск неверного разделения аргументов. Простые удалённые команды с pipeline работали предсказуемее, чем shell substitution.

### 5. Проверка target требует отдельного discovery

Пользователь сначала указал неверное имя учётной записи. Read-only `getent passwd` и `id` предотвратили изменение несуществующего пользователя. Для production-операций relay-adapter должен поощрять обязательную фиксацию:

- hostname;
- SSH-пользователя relay;
- cwd;
- целевого пользователя и home;
- режима sudo;
- фактического target path.

## Рекомендуемые доработки ssh_relay

### P0. Машиночитаемый результат risky-операции

После `exec --risky` и `sudo-exec --risky` CLI может возвращать или опционально печатать JSON с полями:

- session name;
- remote host label;
- command exit code;
- receipt path;
- receipt ID или hash записи;
- sudo mode;
- timestamp.

Это позволит `agent-safe` связать локальную и удалённую транзакции.

### P1. Команда выполнения проверенного скрипта

Вместо сложной inline-команды полезен режим, принимающий локальный обычный файл ограниченного размера:

```text
ssh_relay exec-script --name NAME script.sh
ssh_relay sudo-exec-script --name NAME --risky script.sh
```

Требования:

- содержимое передаётся daemon, а не читается из его cwd;
- hash скрипта включается в receipt;
- shell выбирается явно;
- stdin остаётся закрытым для интерактивного ввода;
- действуют существующие timeout и output limit;
- команда не превращается в произвольную рекурсивную передачу каталогов.

### P1. Discovery-команда для контекста

Опциональная команда наподобие `inspect --name NAME` могла бы вернуть безопасный JSON:

- host/port/user из активной сессии;
- hostname удалённого узла;
- remote cwd;
- включён ли sudo;
- версия relay.

Она не должна выводить token, пароль, ключ или содержимое session-файла.

## Рекомендуемые доработки agent-safe adapter

Специализированный adapter должен поддерживать режим:

```text
safe ssh-relay-risky --relay-mode exec
safe ssh-relay-risky --relay-mode sudo-exec
```

Для `sudo-exec` adapter должен:

- требовать системный receipt path;
- включать режим sudo в expected state;
- выполнять verify тем же режимом, если обычный SSH-пользователь не читает target;
- связывать локальный transaction ID с remote receipt ID;
- не советовать `sudo -n`, если relay использует собственный `sudo-exec`.

## Критерии интеграционного теста

1. Запустить daemon с `--enable-sudo`.
2. Через `safe` создать root-owned тестовый файл командой `sudo-exec --risky`.
3. Подтвердить локальный receipt и удалённый JSONL receipt.
4. Проверить owner/mode через sudo verify.
5. Выполнить rollback и подтвердить состояние.
6. Убедиться, что token и sudo-пароль отсутствуют во всех выводах и receipts.
7. Повторить сценарий с именованными сессиями на двух хостах и доказать отсутствие cross-session target mix-up.

## Операционный вывод

До появления поддержки `sudo-exec` в специализированном adapter допустим generic `safe exec-risky` вокруг `ssh_relay sudo-exec --risky`, если явно заданы target, expected state, rollback, verify и удалённый receipt. Inline JSON и сложные verify-команды в PowerShell следует заменять файлами.
