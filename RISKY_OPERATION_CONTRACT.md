# Машинный контракт risky-операций ssh_relay

## Статус

Контракт версии 1 реализован в `ssh_relay 0.6.0`.

Документ описывает фактический интерфейс `exec` и `sudo-exec` в машинном режиме. Он заменяет прежний проект контракта до кодирования.

Связанные материалы:

- задача [`ssh_relay#2`](https://github.com/dilukhin/ssh_relay/issues/2);
- [`SSH_RELAY_CHANGE_PLAN.md`](SSH_RELAY_CHANGE_PLAN.md);
- [`AGENT_SAFE_INTEGRATION_FINDINGS.md`](AGENT_SAFE_INTEGRATION_FINDINGS.md);
- [`IMPLEMENTATION_REPORT.md`](IMPLEMENTATION_REPORT.md);
- [`MANUAL_TEST_REPORT_0.6.0.md`](MANUAL_TEST_REPORT_0.6.0.md).

## Назначение

Машинный режим позволяет вызывающей стороне однозначно различить:

1. команда достоверно не запускалась;
2. команда завершилась с ненулевым кодом;
3. команда завершилась успешно;
4. risky-команда завершилась успешно и receipt подтверждён;
5. команда завершилась успешно, но receipt не подтверждён;
6. результат самой команды неизвестен.

Timeout, превышение лимита вывода и потеря ответа после возможного запуска команды нельзя представлять как обычный command failure.

## Область контракта

Контракт применяется к:

```text
ssh_relay exec --json
ssh_relay exec --json --risky
ssh_relay sudo-exec --json
ssh_relay sudo-exec --json --risky
```

Обычный текстовый режим сохраняет прежнюю семантику stdout, stderr и удалённого exit code.

Команды `status`, `list`, `download`, `upload` и `stop` в версии 0.6.0 не используют этот JSON-контракт.

## Параметры CLI

```text
--risky
--receipt-path PATH
--json
--transaction-id ID
--change-target TARGET
--change-description TEXT
```

### `--json`

Включает машинный режим результата.

Правила:

- stdout CLI содержит один JSON-объект UTF-8 и завершающий перевод строки;
- удалённые stdout и stderr находятся внутри полей `stdout` и `stderr`;
- при штатно сформированном результате локальный stderr пуст;
- runtime-ошибки relay кодируются полями результата;
- синтаксическая ошибка `argparse`, возникшая до запуска обработчика, может использовать обычный stderr и код `2`.

### `--risky`

После успешной основной команды relay пытается записать безопасный удалённый JSONL receipt.

Receipt не записывается, если:

- операция отклонена до запуска;
- основная команда завершилась с ненулевым кодом;
- результат основной команды неизвестен.

### `--transaction-id`

Идентификатор внешней транзакции.

Допустимый формат:

- длина от 1 до 128 символов;
- первый символ — латинская буква или цифра;
- остальные символы — латинские буквы, цифры, `.`, `_`, `:`, `-`;
- пробелы, переводы строк и управляющие символы запрещены.

Если параметр не задан, relay генерирует UUIDv4 и возвращает:

```text
transaction_id_source = "relay"
```

Если значение передал вызывающий процесс:

```text
transaction_id_source = "caller"
```

Адаптер `agent-safe` должен создавать ID до запуска relay и передавать его явно.

### `--change-target`

Безопасное описание изменяемого объекта.

Примеры:

```text
/home/donpedro/.ssh/authorized_keys
systemd:nginx.service
package:curl
```

Ограничения:

- максимальная длина 1024 символа;
- пустое значение запрещено;
- NUL и управляющие символы запрещены;
- значение не должно содержать пароли, токены и приватные URL.

Если параметр не передан, поле равно `null`. Relay не извлекает target из команды эвристически.

### `--change-description`

Краткое безопасное описание действия.

Ограничения:

- максимальная длина 512 символов;
- пустое значение запрещено;
- управляющие символы запрещены;
- описание не должно содержать секреты.

Если параметр не задан, используется нейтральное описание операции. Полная команда не подставляется вместо описания.

### `--receipt-path`

Путь удалённого JSONL-журнала.

Значение по умолчанию:

```text
~/.local/state/agent-safe/changes.jsonl
```

Путь проверяется на пустое значение, управляющие символы и чрезмерную длину. Конечный путь, являющийся символической ссылкой, отклоняется до основной risky-команды либо при попытке записи.

## Формат результата

Машинный объект содержит следующие поля:

```json
{
  "schema_version": 1,
  "tool": "ssh_relay",
  "tool_version": "0.6.0",
  "action": "sudo-exec",
  "operation_status": "partial_success",
  "session": "prod",
  "remote_host": "198.51.100.42",
  "remote_port": 22,
  "remote_user": "donpedro",
  "sudo": true,
  "risky": true,
  "transaction_id": "agent-safe:tx-001",
  "transaction_id_source": "caller",
  "change_target": "systemd:nginx.service",
  "change_description": "Перезапуск службы",
  "command_status": "succeeded",
  "command_exit_code": 0,
  "command_hash": "sha256:...",
  "receipt_status": "failed",
  "receipt_path": "/var/lib/agent-safe/changes.jsonl",
  "receipt_id": "...",
  "receipt_hash": "sha256:...",
  "previous_receipt_hash": "sha256:...",
  "partial_success": true,
  "stdout": "",
  "stderr": "",
  "output_encoding": "utf-8-replace",
  "error_code": "receipt_write_failed",
  "error_stage": "receipt",
  "error_message": "Удалённая команда выполнена, но receipt записать не удалось.",
  "started_at_utc": "2026-07-31T12:00:00Z",
  "finished_at_utc": "2026-07-31T12:00:01Z"
}
```

Недоступные значения передаются как `null`, если поле не имеет отдельного строкового статуса.

## Значения `action`

- `exec`;
- `sudo-exec`.

Поле соответствует пользовательской подкоманде CLI.

## Значения `operation_status`

### `succeeded`

Для нерискованной операции:

- команда завершилась с кодом `0`.

Для risky-операции:

- команда завершилась с кодом `0`;
- receipt записан и подтверждён контрольным чтением.

### `command_failed`

- удалённая команда завершилась с ненулевым кодом;
- точный код находится в `command_exit_code`;
- receipt не записывается.

### `partial_success`

- команда достоверно завершилась с кодом `0`;
- receipt имеет статус `failed` или `unknown`;
- удалённое состояние уже могло измениться;
- вызывающая сторона должна выполнить read-only verify, поиск receipt или rollback.

### `not_started`

Достоверно известно, что основная команда не запускалась.

Примеры:

- session-файл отсутствует или повреждён;
- daemon недоступен до отправки запроса;
- daemon не поддерживает требуемую версию протокола;
- sudo не включён;
- preflight receipt завершился ошибкой;
- `transaction_id` уже присутствует в журнале.

### `unknown`

Точный результат основной команды получить невозможно.

Примеры:

- timeout после запуска удалённого канала;
- превышение лимита вывода после начала команды;
- потеря ответа daemon после отправки запроса;
- повреждённый или неполный ответ после возможного выполнения.

Такой исход нельзя автоматически повторять как будто команда не запускалась.

## Значения `command_status`

- `not_started`;
- `succeeded`;
- `failed`;
- `unknown`.

`command_exit_code`:

- содержит `0` для `succeeded`;
- содержит точный ненулевой удалённый код для `failed`;
- равен `null` для `not_started` и `unknown`.

Наличие текста в удалённом stderr само по себе не определяет результат команды.

## Значения `receipt_status`

- `written` — строка добавлена и подтверждена;
- `failed` — запись достоверно завершилась ошибкой;
- `unknown` — запись могла произойти, но подтверждение не получено;
- `not_attempted` — запись не начиналась из-за результата основной команды или preflight;
- `not_requested` — операция выполнена без `--risky`.

Для risky-операции `receipt_id` создаётся заранее. При `failed` или `unknown` вызывающая сторона может искать предполагаемую запись по этому ID.

## Правило `partial_success`

Поле `partial_success` равно `true` только при условии:

```text
command_status == "succeeded"
и
receipt_status входит в {"failed", "unknown"}
```

В остальных состояниях оно равно `false`.

## Hash команды

`command_hash` вычисляется как SHA-256 от точных UTF-8 байтов пользовательской команды:

```text
sha256(command.encode("utf-8"))
```

Формат:

```text
sha256:<64 шестнадцатеричных символа нижнего регистра>
```

Для `sudo-exec` hash вычисляется от пользовательской команды без автоматически добавляемой sudo-оболочки.

Полный текст команды не включается ни в машинный результат, ни в новый receipt 0.6.0.

## Формат удалённого receipt

JSONL-запись содержит:

```json
{
  "schema_version": 1,
  "timestamp_utc": "2026-07-31T12:00:01Z",
  "tool": "ssh_relay",
  "tool_version": "0.6.0",
  "session": "prod",
  "remote_host": "198.51.100.42",
  "remote_port": 22,
  "remote_user": "donpedro",
  "action": "sudo-exec",
  "sudo": true,
  "transaction_id": "agent-safe:tx-001",
  "receipt_id": "...",
  "change_target": "systemd:nginx.service",
  "change_description": "Перезапуск службы",
  "command_status": "succeeded",
  "command_hash": "sha256:...",
  "command_exit_code": 0,
  "previous_receipt_hash": "sha256:...",
  "receipt_hash": "sha256:..."
}
```

Receipt не содержит:

- полный текст команды;
- stdout;
- stderr;
- SSH-пароль;
- sudo-пароль;
- токен session-файла;
- приватный ключ.

## Канонический `receipt_hash`

1. Из объекта исключается поле `receipt_hash`.
2. JSON сериализуется с сортировкой ключей, без лишних пробелов и с `ensure_ascii=false`.
3. Результат кодируется UTF-8.
4. Вычисляется SHA-256.
5. Используется строковый формат `sha256:<hex>`.

`previous_receipt_hash` содержит проверенный self-hash предыдущей новой записи.

Последняя запись формата 0.5.x может быть принята как однократный legacy anchor, если содержит ожидаемые старые поля `tool=ssh_relay`, `status=done` и строковую команду. Её канонический hash становится `previous_receipt_hash` первой записи 0.6.0. Старая команда не переносится в новую запись.

## Preflight risky-операции

До запуска основной команды relay:

1. проверяет путь receipt;
2. отклоняет конечную символическую ссылку;
3. читает последнюю непустую строку, если журнал существует;
4. проверяет self-hash либо legacy anchor;
5. проверяет отсутствие `transaction_id` в журнале.

Если preflight не завершён достоверно, операция получает `not_started`.

Повторный `transaction_id` блокируется, но это не делает команду автоматически идемпотентной. Политику повторного запуска определяет вызывающая сторона.

## Запись и подтверждение receipt

Relay:

- использует `umask 077`;
- создаёт родительский каталог при необходимости;
- создаёт файл и задаёт режим `0600`;
- добавляет одну JSONL-строку;
- читает последнюю строку;
- проверяет `receipt_id`;
- проверяет `receipt_hash`.

Если append мог произойти, но контрольное чтение не подтвердило запись, используется `receipt_status=unknown`, а вся операция становится `partial_success`.

Сторонние параллельные писатели в тот же журнал не поддерживаются. Доверенный родительский каталог остаётся обязанностью оператора.

## stdout и stderr

- удалённый stdout хранится в поле `stdout`;
- удалённый stderr хранится в поле `stderr`;
- декодирование выполняется UTF-8 с заменой повреждённых последовательностей;
- общий лимит вывода остаётся 4 МиБ;
- relay не пытается редактировать произвольный вывод команды.

Команда не должна выводить секреты. JSON-режим структурирует вывод, но не делает содержимое удалённого stdout/stderr безопасным.

## Поля ошибки

- `error_code` — стабильный машинный идентификатор;
- `error_stage` — стадия;
- `error_message` — русская диагностика без намеренного включения секретов.

Используемые стадии:

- `session`;
- `daemon`;
- `command`;
- `receipt`;
- `protocol`.

Примеры кодов:

- `session_unavailable`;
- `daemon_unavailable`;
- `daemon_response_lost`;
- `sudo_disabled`;
- `command_failed`;
- `command_timeout`;
- `output_limit_exceeded`;
- `receipt_preflight_failed`;
- `transaction_id_exists`;
- `receipt_write_failed`;
- `receipt_status_unknown`;
- `response_invalid`.

Точный набор кодов определяется реализацией 0.6.x и должен оставаться обратно совместимым в пределах версии контракта.

## Коды завершения процесса

| Код | Значение |
|---:|---|
| `0` | операция успешна |
| `10` | операция достоверно не запущена |
| `11` | удалённая команда завершилась с ненулевым кодом |
| `12` | команда успешна, receipt имеет `failed` или `unknown` |
| `13` | результат основной команды неизвестен |
| `2` | синтаксическая ошибка CLI до формирования результата |

Точный удалённый exit code при локальном коде `11` находится в `command_exit_code`.

## Совместимость текстового режима

Без `--json`:

- удалённый stdout печатается в stdout;
- удалённый stderr печатается в stderr;
- возвращается удалённый exit code;
- ошибка relay возвращает `1` с русской диагностикой;
- при partial success возвращается `1` и сообщается, что основная команда уже выполнена.

## Совместимость версий

- daemon 0.6.0 принимает обычные запросы CLI 0.5.x;
- CLI 0.6.0 допускает обычную нерискованную команду через старый daemon;
- `--json` и новая risky-семантика требуют daemon с поддержкой протокола 0.6.0;
- после обновления daemon необходимо перезапустить.

## Ответственность `agent-safe`

В `ssh_relay` не переносятся:

- классификация риска;
- подтверждение пользователя;
- expected state;
- verify-политика;
- rollback;
- блокировка общего transaction workflow;
- решение о повторном запуске после `unknown` или `partial_success`.

Relay предоставляет транспорт, идентификаторы, удалённый receipt и машинно различимый результат.

## Состояние проверки

Подтверждено:

- синтаксис Python;
- локальная матрица машинных состояний;
- self-hash и legacy anchor;
- отсутствие полного текста команды в тестовом receipt;
- повторный `transaction_id`;
- сохранение session-файла при потерянном ответе;
- локальный TCP-протокол с подменённым SSH-транспортом;
- реальный smoke-тест `exec`, `sudo-exec`, удалённого exit code и успешного нерискованного JSON.

Для полной приёмки Issue #2 ещё требуются:

- реальный `exec --json --risky` с записью JSONL на Linux;
- реальный `sudo-exec --json --risky`;
- фактический сбой и неизвестный статус receipt после успешной команды;
- реальный сетевой разрыв или timeout после запуска;
- две именованные сессии без смешения host, target и receipt;
- интеграция с `agent-safe`.
