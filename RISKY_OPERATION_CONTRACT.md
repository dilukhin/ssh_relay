# Машинный контракт risky-операций ssh_relay

## Статус

Документ фиксирует предлагаемый контракт версии 1 для дальнейшей реализации в `ssh_relay 0.6.0`.

Код в рамках подготовки контракта не изменяется. До начала кодирования требуется согласовать этот документ вместе со схемой удалённого receipt и правилами `partial_success`.

Связанные материалы:

- findings: [`AGENT_SAFE_INTEGRATION_FINDINGS.md`](AGENT_SAFE_INTEGRATION_FINDINGS.md);
- план: [`SSH_RELAY_CHANGE_PLAN.md`](SSH_RELAY_CHANGE_PLAN.md);
- задача `ssh_relay`: [#2](https://github.com/dilukhin/ssh_relay/issues/2);
- зависимая задача `agent-safe`: [dilukhin/agent-safe#4](https://github.com/dilukhin/agent-safe/issues/4).

## Назначение

Машинный режим должен позволять вызывающей стороне однозначно определить:

1. команда не была запущена;
2. команда завершилась с ненулевым кодом;
3. команда завершилась успешно и receipt записан;
4. команда завершилась успешно, но receipt не записан;
5. relay не может достоверно определить результат команды или записи receipt.

Контракт применяется к:

```text
ssh_relay exec --risky
ssh_relay sudo-exec --risky
```

Обычный текстовый режим сохраняет существующую семантику и не обязан выдавать JSON.

## Предлагаемые параметры CLI

```text
--json
--transaction-id ID
--change-target TARGET
--change-description TEXT
```

### `--json`

Включает машинный режим результата.

Правила:

- stdout CLI содержит ровно один JSON-объект UTF-8 и завершающий перевод строки;
- удалённые stdout и stderr не печатаются отдельно, а включаются в поля `stdout` и `stderr`;
- runtime-диагностика relay включается в поля ошибки JSON;
- stderr локального CLI в штатно разобранном машинном режиме остаётся пустым;
- синтаксические ошибки `argparse`, возникшие до запуска обработчика, могут выводиться обычным способом и завершаться кодом `2`.

`--json` должен поддерживаться у `exec` и `sudo-exec`. В первой реализации контракт обязателен прежде всего для операций с `--risky`.

### `--transaction-id`

Идентификатор внешней транзакции.

Правила:

- допустимы латинские буквы, цифры, точка, подчёркивание, двоеточие и дефис;
- первый символ — буква или цифра;
- длина — от 1 до 128 символов;
- значение не должно содержать пробелы, переводы строк и управляющие символы;
- если параметр не задан, relay генерирует UUIDv4;
- источник значения отражается в поле `transaction_id_source`: `caller` или `relay`.

`agent-safe` должен всегда передавать собственный локальный transaction ID.

### `--change-target`

Безопасное описание изменяемого объекта, например:

```text
/home/donpedro/.ssh/authorized_keys
systemd:nginx.service
package:curl
```

Правила:

- значение не должно включать пароль, токен, приватный URL или другие секреты;
- максимальная длина — 1024 символа;
- запрещены NUL и управляющие символы, кроме обычного пробела;
- параметр рекомендуется для ручного запуска и обязателен на уровне адаптера `agent-safe`.

Если значение не передано, поле `change_target` равно `null`. Relay не пытается извлекать target из текста команды эвристически.

### `--change-description`

Краткое безопасное описание действия, например:

```text
Добавление ограниченного публичного ключа
Перезапуск службы после изменения конфигурации
```

Правила:

- максимальная длина — 512 символов;
- запрещены NUL, переводы строк и другие управляющие символы;
- значение не должно содержать секреты;
- если параметр не задан, используется нейтральное значение `Удалённое изменение`.

Relay не сохраняет полную команду вместо описания.

## Формат результата

Все перечисленные поля присутствуют всегда. Недоступные значения передаются как `null`, а не удаляются из объекта.

```json
{
  "schema_version": 1,
  "tool": "ssh_relay",
  "tool_version": "0.6.0",
  "action": "sudo-exec",
  "operation_status": "partial_success",
  "session": "prod",
  "remote_host": "198.51.100.42",
  "remote_port": 22,
  "remote_user": "donpedro",
  "sudo": true,
  "risky": true,
  "transaction_id": "agent-safe:01JABCDEF0123456789",
  "transaction_id_source": "caller",
  "change_target": "/home/donpedro/.ssh/authorized_keys",
  "change_description": "Добавление ограниченного публичного ключа",
  "command_status": "succeeded",
  "command_exit_code": 0,
  "command_hash": "sha256:...",
  "receipt_status": "failed",
  "receipt_path": "/var/lib/agent-safe/changes.jsonl",
  "receipt_id": "...",
  "receipt_hash": "sha256:...",
  "previous_receipt_hash": "sha256:...",
  "partial_success": true,
  "stdout": "",
  "stderr": "",
  "output_encoding": "utf-8-replace",
  "error_code": "receipt_write_failed",
  "error_stage": "receipt",
  "error_message": "Удалённая команда выполнена, но receipt записать не удалось.",
  "started_at_utc": "2026-07-27T14:30:00Z",
  "finished_at_utc": "2026-07-27T14:30:01Z"
}
```

## Значения `action`

Допустимы:

- `exec`;
- `sudo-exec`.

Поле соответствует пользовательской команде CLI, а не внутреннему имени daemon-действия.

## Значения `operation_status`

### `succeeded`

Команда завершилась с кодом `0`, receipt достоверно записан.

### `command_failed`

Удалённая команда завершилась с ненулевым кодом. Receipt не записывается.

### `partial_success`

Команда достоверно завершилась с кодом `0`, но receipt:

- не записан;
- либо результат его записи неизвестен.

Удалённое состояние уже могло измениться. Требуется verify, rollback либо ручная проверка.

### `not_started`

Relay достоверно отклонил операцию до запуска удалённой команды. Примеры:

- сессия отсутствует;
- daemon недоступен до отправки запроса;
- режим sudo не включён;
- параметры запроса не прошли проверку.

### `unknown`

Relay не может достоверно установить, выполнялась ли команда или как она завершилась. Примеры:

- истёк timeout после передачи команды удалённому каналу;
- соединение разорвано после отправки запроса daemon;
- превышен лимит вывода после начала команды;
- ответ daemon повреждён после возможного выполнения операции.

Такой исход нельзя автоматически считать `command_failed`.

## Значения `command_status`

- `not_started` — команда достоверно не запускалась;
- `succeeded` — получен exit code `0`;
- `failed` — получен ненулевой exit code;
- `unknown` — точный результат получить невозможно.

`command_exit_code`:

- содержит точный удалённый exit code для `succeeded` и `failed`;
- равен `null` для `not_started` и `unknown`.

## Hash команды

`command_hash` вычисляется как SHA-256 от точных UTF-8 байтов пользовательского аргумента команды:

```text
sha256(command.encode("utf-8"))
```

Формат поля:

```text
sha256:<64 шестнадцатеричных символа в нижнем регистре>
```

Для `sudo-exec` hash вычисляется от пользовательской команды без автоматически добавляемой оболочки `sudo -S ... sh -c`.

Полный текст команды в машинный результат и удалённый receipt не включается.

## Значения `receipt_status`

- `written` — receipt достоверно добавлен в журнал;
- `failed` — запись receipt достоверно завершилась ошибкой;
- `unknown` — запись могла произойти, но подтверждение не получено;
- `not_attempted` — запись не начиналась из-за ошибки команды или отказа до запуска;
- `not_requested` — операция выполнена без `--risky`.

Для risky-операции с успешной командой `receipt_id` создаётся до попытки записи. Поэтому при `failed` или `unknown` вызывающая сторона получает идентификатор предполагаемой записи и может выполнить read-only поиск в журнале.

`receipt_hash` и `previous_receipt_hash` определяются отдельной схемой удалённого receipt. До её согласования эти поля в контракте зарезервированы и могут быть `null`.

## Правило `partial_success`

Поле равно `true`, только когда:

```text
command_status == "succeeded"
и
receipt_status входит в {"failed", "unknown"}
```

Во всех остальных случаях поле равно `false`.

## stdout и stderr

В машинном режиме:

- `stdout` содержит удалённый stdout;
- `stderr` содержит удалённый stderr;
- оба значения декодируются UTF-8 с заменой повреждённых последовательностей, как в текущей реализации;
- общий существующий лимит вывода 4 МиБ сохраняется;
- наличие текста в `stderr` само по себе не означает ошибку;
- полный удалённый exit code хранится отдельно в `command_exit_code`.

Relay не сохраняет stdout и stderr в удалённый receipt.

Вызывающая сторона должна учитывать, что сама удалённая команда способна вывести секрет. Машинный режим не может безопасно редактировать произвольный вывод без потери данных.

## Ошибки

Поля ошибки:

- `error_code` — стабильный машинный код;
- `error_stage` — этап возникновения;
- `error_message` — русская диагностика для оператора без секретов.

Предлагаемые значения `error_stage`:

- `cli`;
- `session`;
- `daemon`;
- `command`;
- `receipt`;
- `protocol`.

Минимальный набор `error_code`:

- `invalid_arguments`;
- `session_unavailable`;
- `daemon_unavailable`;
- `sudo_disabled`;
- `command_failed`;
- `command_timeout`;
- `output_limit_exceeded`;
- `receipt_write_failed`;
- `receipt_status_unknown`;
- `response_invalid`;
- `outcome_unknown`;
- `internal_error`.

При `operation_status == "succeeded"` поля ошибки равны `null`.

## Коды завершения процесса в машинном режиме

| Код | Значение |
|---:|---|
| `0` | команда успешна, receipt записан |
| `10` | операция достоверно не запущена либо отклонена relay |
| `11` | удалённая команда завершилась с ненулевым кодом |
| `12` | команда успешна, receipt завершился `failed` или `unknown` |
| `13` | результат удалённой команды неизвестен |
| `2` | синтаксическая ошибка CLI до формирования машинного результата |

Точный удалённый exit code при машинном коде `11` находится в `command_exit_code`.

Коды `10`–`13` применяются только при `--json`. Это исключает смешение транспортной ошибки с удалённым exit code и позволяет адаптеру принимать решение без разбора текста.

## Совместимость текстового режима

Без `--json` сохраняется существующее поведение:

- удалённый stdout печатается в stdout;
- удалённый stderr печатается в stderr;
- вызывающему процессу возвращается удалённый exit code;
- ошибка relay сопровождается русской диагностикой и кодом `1`.

Изменение внутреннего формата receipt не должно менять вывод обычной успешной команды.

Для частичного успеха текстовый режим должен явно сообщить:

```text
Удалённая команда выполнена успешно, но receipt записать не удалось. Состояние хоста изменено; требуется проверка.
```

Текстовый режим может вернуть код `1` для обратной совместимости. Надёжное машинное различение гарантируется только с `--json`.

## Матрица результатов

| Сценарий | operation_status | command_status | receipt_status | partial_success | process code |
|---|---|---|---|---:|---:|
| Команда `0`, receipt записан | `succeeded` | `succeeded` | `written` | false | 0 |
| Команда завершилась `7` | `command_failed` | `failed` | `not_attempted` | false | 11 |
| Команда `0`, запись receipt отклонена | `partial_success` | `succeeded` | `failed` | true | 12 |
| Команда `0`, подтверждение receipt потеряно | `partial_success` | `succeeded` | `unknown` | true | 12 |
| Режим sudo не включён | `not_started` | `not_started` | `not_attempted` | false | 10 |
| Timeout после запуска команды | `unknown` | `unknown` | `not_attempted` | false | 13 |
| Ответ daemon потерян после отправки | `unknown` | `unknown` | `unknown` | false | 13 |

## Безопасность

Контракт не должен приводить к сохранению или выводу:

- session token;
- SSH-пароля;
- sudo-пароля;
- passphrase ключа;
- приватного ключа;
- полной команды;
- внутренней receipt-команды shell;
- содержимого session-файла.

Поля `change_target`, `change_description`, stdout и stderr поступают от пользователя или удалённой команды. Relay обязан документировать, что вызывающая сторона не должна помещать в них секреты.

Токен локальной сессии остаётся только во внутреннем запросе CLI к daemon и не включается в JSON-результат.

## Требования к daemon-протоколу

Daemon должен возвращать CLI структурированный результат, достаточный для формирования контракта без анализа русских сообщений.

Нужно отдельно различать:

- отказ до запуска команды;
- полученный удалённый exit code;
- исключение после запуска команды;
- успешную команду и достоверную ошибку receipt;
- успешную команду и неизвестный статус receipt.

Русское поле `protocol_error` не должно оставаться единственным источником состояния.

Версия машинной схемы результата не обязана совпадать с версией внутреннего daemon-протокола.

## Открытые вопросы следующего этапа

До кодирования остаётся согласовать схему удалённого receipt:

1. каноническое JSON-представление;
2. алгоритм и область вычисления `receipt_hash`;
3. правила `previous_receipt_hash`;
4. атомарность чтения последнего hash и добавления записи;
5. поведение при повреждённой последней строке;
6. способ проверки, был ли receipt записан после потери подтверждения;
7. допустимость отдельного явного режима хранения полной команды.

После этого требуется окончательно проверить правила `partial_success` при разрыве соединения на каждом этапе.

## Критерии согласования этапа 1

Этап 1 считается согласованным после подтверждения следующих решений:

- используется флаг `--json`;
- JSON занимает stdout целиком;
- удалённые stdout/stderr включаются в JSON;
- transaction ID всегда присутствует и генерируется relay при отсутствии внешнего значения;
- полный текст команды не входит в JSON и receipt;
- машинные process exit codes равны `0`, `10`, `11`, `12`, `13`;
- timeout и потеря ответа после запуска не выдаются за обычный command failure;
- текстовый режим сохраняет текущую семантику.
