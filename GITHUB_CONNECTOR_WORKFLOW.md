# Регламент работы с GitHub-коннектором

Этот документ фиксирует порядок безопасной работы с подключённым GitHub-приложением из ChatGPT. Он дополняет инструкции проекта и применяется к изменениям в репозитории `dilukhin/ssh_relay`.

## Термины

В интерфейсе ChatGPT поле с постоянными правилами проекта называется **«Инструкции проекта»** (`Project instructions`). Выражение «системный промпт проекта» допустимо как неформальное обозначение, но это не название элемента интерфейса.

Под **GitHub-коннектором** здесь понимается подключённое к ChatGPT GitHub-приложение с доступными операциями чтения и записи. Набор операций может изменяться, поэтому перед публикацией необходимо проверить фактически доступные схемы инструментов.

## Общие правила

1. Источник истины — фактическое содержимое файлов и состояние ветки GitHub.
2. Перед записью определить репозиторий, рабочую ветку и текущий HEAD.
3. Не считать локальный путь вида `/mnt/data/file` содержимым файла. Коннектор не обязан разыменовывать такие пути.
4. Не выполнять `force`-обновление ветки.
5. Не передвигать branch ref, пока не проверены все создаваемые blobs и commit.
6. Не утверждать, что commit или push выполнен, пока новый HEAD ветки не прочитан и не подтверждён.
7. Не передавать в GitHub токены, пароли, session-файлы, приватные ключи и другие секреты.

## Небольшие текстовые изменения

Для создания или замены одного небольшого UTF-8 файла допускается использовать операции Contents API:

1. прочитать существующий файл и получить его blob SHA;
2. вызвать `create_file` либо `update_file` с полным текстом;
3. повторно прочитать файл из целевой ветки;
4. проверить содержимое и новый commit SHA.

Следует учитывать, что последовательные вызовы `create_file` и `update_file` создают отдельный commit для каждого файла. Такой режим не является атомарным многофайловым commit.

## Публикация локальных файлов и комплектов

Если файл создан в sandbox ChatGPT, наличие пути `/mnt/data/...` само по себе не означает, что GitHub-коннектор может получить его байты.

Безопасный порядок:

1. прочитать фактические байты локального файла;
2. вычислить SHA-256 файла для контроля артефакта;
3. вычислить Git blob SHA для этих байтов: SHA-1 от `blob <размер>\0<байты>`;
4. передать полное содержимое в `create_blob` как UTF-8 либо base64;
5. сравнить SHA, возвращённый GitHub, с вычисленным Git blob SHA;
6. при необходимости прочитать blob обратно и сравнить содержимое;
7. повторить проверку для каждого файла;
8. создать tree поверх tree текущего HEAD;
9. создать один commit с ожидаемым parent SHA;
10. передвинуть ref рабочей ветки без `force`;
11. повторно прочитать HEAD, commit и критичные файлы.

Если коннектор не предоставляет безопасный способ получить base tree, передать полный файл без обрезки или проверить blob, публикацию следует остановить до изменения ветки. В этом случае используется локальный `git` или `gh`.

## Проверка конкурентных изменений

Перед созданием commit фиксируется `expected_head`. Непосредственно перед `update_ref` необходимо повторно проверить HEAD ветки.

Если HEAD изменился:

- ref не передвигать;
- новый commit не считать опубликованным;
- повторно изучить diff и пересобрать commit поверх актуального HEAD.

Недостижимые blobs, trees или commits не изменяют ветку и могут остаться в объектном хранилище GitHub; это допустимо. Недопустимо передвигать ref на непроверенный commit.

## Проверки кода

GitHub-коннектор не заменяет локальный запуск тестов.

До публикации должны быть фактически выполнены доступные локальные проверки. После публикации следует проверить CI, если он настроен. Для `ssh_relay.py` минимально проверяются:

```text
python -m py_compile ssh_relay.py
python tests/test_machine_protocol.py
python tests/test_local_tcp_protocol.py
python ssh_relay.py --version
```

При изменении daemon перед ручным тестированием его необходимо остановить и запустить заново.

## Отчёт о публикации

После успешной записи сообщаются:

- репозиторий;
- ветка;
- предыдущий и новый HEAD;
- commit message;
- список файлов;
- фактически выполненные проверки;
- проверки, которые не выполнялись;
- наличие или отсутствие CI.

При ошибке явно сообщается последняя подтверждённая стадия. Нельзя писать «commit выполнен» или «push выполнен», если ref ветки не был подтверждён после записи.
