# SSH к узлу за NAT через посредника — кандидат 0.14.0, задача #54

Конечный узел сам поддерживает обратный SSH-туннель до доступного VPS. Relay
подключается к VPS, открывает `direct-tcpip` к обратному порту и внутри этого
канала устанавливает отдельное SSH-соединение с конечным узлом. Установка
ssh_relay на VPS для этого не требуется. Обратный туннель запускается отдельно;
relay его не создаёт и не останавливает.

## Как задать маршрут

Например, на конечном ПК уже работает OpenSSH Server, слушающий 127.0.0.1:22.
Пользователь запускает и поддерживает на нём отдельный процесс OpenSSH:

```text
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -R 127.0.0.1:2222:127.0.0.1:22 dilukhin@185.79.138.72
```

При выходе этого процесса туннель исчезает. Политику его автоматического запуска
и восстановления на ПК нужно настраивать отдельно. Порт 2222 слушает только
loopback VPS; публиковать его на 0.0.0.0 не требуется. На VPS должны быть
разрешены обратный проброс для создающего туннель пользователя и локальный
проброс для пользователя relay. `AllowTcpForwarding yes` разрешает оба вида;
при ограничении `PermitOpen` нужно разрешить ровно `127.0.0.1:2222` для relay.
`PermitListen` для обратного туннеля можно ограничить тем же адресом и портом.
Изменения sshd сначала проверяются `sshd -t`; рабочее соединение администратора
сохраняют до проверки нового. Настройка VPS и пользовательского ПК в этом PR
не выполнялась.

На машине relay:

```text
ssh_relay daemon --name home-via-vserv --host DIMA-HP --user Dima --via-host 185.79.138.72 --via-user dilukhin --via-target-port 2222 --identity-file PC_KEY --via-identity-file VPS_KEY --known-hosts PC_KNOWN_HOSTS --via-known-hosts VPS_KNOWN_HOSTS
ssh_relay status --name home-via-vserv --json
ssh_relay exec --name home-via-vserv "hostname"
ssh_relay stop --name home-via-vserv
```

Имена файлов в примере заменить своими путями. `--host DIMA-HP` обозначает
уникальное имя конечного ПК для проверки его ключа, а не сетевое назначение.
Relay не пытается соединиться с этим именем по DNS. В PC_KNOWN_HOSTS должна быть
заранее проверенная запись `DIMA-HP <тип> <публичный ключ ПК>`; ключ VPS
проверяется по 185.79.138.72 в другом файле. Полученный по сети ключ нельзя
автоматически считать доверенным: его отпечаток сверяют независимым способом.
Не используйте одно имя ПК для нескольких машин. При нестандартном `--port`
запись конечного узла имеет вид `[DIMA-HP]:<port>`.

`--port` по умолчанию 22 и задаёт идентичность конечного SSH-сервера.
`--via-port` по умолчанию 22 — SSH-порт VPS. `--via-target-port 2222` — фактический
TCP-порт обратного туннеля на VPS. `--via-target-host` по умолчанию 127.0.0.1.
При указании посредника обязательны отдельные `--via-user` и `--via-target-port`.

Для каждого соединения можно отдельно указать ключ или ввести пароль.
Зашифрованные ключи требуют соответственно `--ask-key-passphrase` и
`--via-ask-key-passphrase`. Пароли остаются в памяти daemon и не записываются
в параметры процесса, состояние сессии или квитанции. Для `--detach` нужны оба
ключа без интерактивных запросов. SSH-agent и автоматический подбор ключей
не включаются; неизвестный или изменившийся ключ любого узла отклоняется.

## Состояние, обрыв и ограничения

В JSON `verified_identity` продолжает обозначать конечный узел. Схема и проверки
квитанций остаются прежними. `ssh_route` описывает запрошенный маршрут,
а `verified_intermediate_identity` содержит ключ активного проверенного VPS.
Описание маршрута само по себе не является подтверждённой идентичностью.
При потере любого соединения daemon пересоздаёт оба и повышает поколение
конечной identity. Старый pin больше не подходит. Получив `unknown`, нужно
проверить результат операции; автоматического повторного выполнения нет.

Недоступный обратный порт или запрет проброса возвращают ошибку, без попытки
прямого подключения к ПК. `stop` закрывает только соединения данного relay,
оставляя независимый процесс обратного туннеля. Прямое подключение без
`--via-*` сохраняет прежний путь исполнения.

Этот маршрут меняет транспорт. Он не добавляет совместимость Linux-команд,
systemd, sudo-job или квитанций с Windows как удалённой ОС. Для Windows отдельно
нужно проверить установленный OpenSSH Server, разрешения, оболочку команд и
SFTP-пути. В автоматическом испытании конечный SSH/SFTP-сервер — изолированный
Paramiko-сервер; обратный туннель использует настоящие SSH `tcpip-forward` и
`forwarded-tcpip`, а relay — настоящий `direct-tcpip`. Это не приёмка реального
DIMA-HP или системного OpenSSH `ssh -R`.

## Проверки кандидата

`tests/test_ssh_route.py` проверяет маршрут, отказ и закрытие ресурсов при
неудачном подключении, оба неизвестных/неверных ключа, отсутствующий туннель,
запрет проброса, команды, SFTP и CLI upload/download, reconnect, неприменимость
старого pin и сохранение независимого туннеля после stop. Повторён прежний
контракт verified exec и sudo на синтетическом сервере; root-команды не
выполняются. Локально в среде ChatGPT отсутствует Paramiko, поэтому реальные
SSH-проверки выполняются обязательным CI на Ubuntu и Windows. Слияние, выпуск
и приёмка на пользовательском ПК проверяются отдельно.
