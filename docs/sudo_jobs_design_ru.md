# Длительные задания с sudo: решение по #52

Статус: реализован кандидат версии 0.12.0 поверх PR #51. Выпуск поддерживаемой
сборки требует испытаний и отдельной интеграции с agent-safe; задача #52 не
закрывается одним наличием кода. Основная ветка и пользовательские VPS не меняются.

## Выбор реализации

| Вариант | Преимущества | Ограничения | Решение |
| --- | --- | --- | --- |
| Расширить обычный `job` | Существующие команды и наблюдение | Пользовательские каталоги и PID не обеспечивают защиту команды root; потребовалась бы отдельная реализация хранения и владения | Оставить без изменений |
| Короткий вызов sudo запускает службу systemd | Служба переживает SSH и локальный daemon; есть группа процессов, UUID запуска и явные сигналы | Нужны systemd, Python 3 и cgroup v2 на удалённом узле | Выбрано |
| Постоянный удалённый помощник | Можно задать более узкие полномочия | Установка, обновление, аутентификация и дополнительная служба | Не требуется для первого сценария |

`sudo-job start/status/tail/wait/stop` использует небольшой передаваемый помощник
root. Он запускается через `/usr/bin/python3 -I -c` и sudo. Для самого длительного
задания сохраняется копия наблюдателя в защищённом каталоге root. Постоянная
служба-посредник и весь интерфейс RemoteProcessSpec не вводятся. Строковые
`exec`, `sudo-exec` и обычный `job` сохраняют свои прежние контракты.

## Доверие и ограничения

1. Пользователь запускает daemon с **обоими** параметрами `--enable-sudo` и
   `--enable-sudo-jobs`. Пароль вводит пользователь; агент получает только
   зарегистрированную сессию. Одного разрешения коротких sudo-команд недостаточно.
2. Клиент и daemon обязаны иметь один полный SHA сборки. Перед каждой операцией
   проверяется точное ожидание из PR #51: адрес, порт, пользователь, алгоритм и
   отпечаток ключа, экземпляр daemon, поколение соединения и SHA. Повторная проверка
   выполняется внутри заблокированного запроса перед отправкой через SSH.
3. Файл ожидания не является разрешением человека. Отпечаток ключа должен быть
   подтверждён независимо; нельзя объявлять полученный от неизвестного сервера
   ключ доверенным только потому, что он присутствует в `status`.
4. `sudo -k -S` не использует существующий временный допуск. Пароль отправляется
   только после уникального приглашения sudo. Помощник сообщает READY после
   успешного повышения прав; лишь затем передаются байты полезного запроса.
   При NOPASSWD пароль не отправляется вообще. Ни argv, ни окружение root-команды,
   ни файлы, журналы и свидетельства пароля не содержат.
5. `/var/lib/ssh-relay-sudo-jobs` и каталоги заданий принадлежат root и имеют права
   0700, файлы — 0600. Проверяются все предки, тип файлов, владелец, права,
   отсутствие символических и дополнительных жёстких ссылок. Не используется
   заранее загруженный обычным SSH-пользователем скрипт. SHA-256 команды
   проверяется непосредственно перед запуском `/bin/sh -c` из защищённых байт.
6. Текущий доверенный администратор root и намеренно опасная разрешённая
   root-команда находятся вне защиты механизма. Подмена обычным SSH-пользователем
   исключается правами каталогов. Доверие к системе и ключу SSH остаётся условием.
7. Удалённая сторона: Linux, systemd как PID 1, cgroup v2, `/usr/bin/python3`,
   `/usr/bin/systemd-run`, `/usr/bin/systemctl`, `/bin/sh`. Образы Ubuntu 22.04 и
   24.04 включены в отдельные испытания. Контейнер без systemd, OpenRC и cgroup v1
   отклоняются до создания задания. Команды неинтерактивны: stdin — `/dev/null`,
   рабочий каталог — `/`, окружение фиксировано (`PATH`, `HOME=/root`, `LANG`).

Полный текст команды хранится **только** в защищённом `command.json` root;
свидетельства содержат её SHA-256. Текст команды не надо использовать для
передачи секретов. Обычная команда может сама вывести свои секреты — содержимое
её журналов не является безопасным свидетельством.

## Жизненный цикл

До любой мутации вызывающая сторона сохраняет `job_id`, `transaction_id` (два
UUID) и SHA-256 точных UTF-8 байт команды. Идентификаторы задаются обязательно,
а не генерируются после успешного ответа. В root-каталоге резервируются UUID
задания и транзакции. Повторное использование запрещено, включая завершённые
задания. Резервирование сериализовано `flock`; PID не является идентификатором.

| Результат | Значение | Следующее действие |
| --- | --- | --- |
| `not_started` | Эта попытка запуска отклонена до создания/запуска полезной команды | Проверить причину; уже существующее задание имеет отдельное состояние |
| `running` | Наблюдатель службы подтверждён и задание не завершено | Только наблюдать |
| `succeeded`, `exit_code=0` | Команда и её оставшиеся потомки завершены | Проверить свидетельство и ожидаемое состояние установки |
| `failed`, точный `exit_code` | Сохранён ненулевой исход команды | Проверка состояния и согласованное восстановление |
| `unknown` | Возможный запуск или исход не удалось достоверно установить | Только чтение; автоматического повтора нет |

`start_witness` связывает задание, транзакцию, цель, hash команды, boot ID,
имя unit и systemd InvocationID. Он подтверждает наблюдателя запуска, а не
успешную установку. `completion_witness` добавляет точный код, время завершения
и счётчики ограниченного вывода. Каждый документ имеет SHA-256 канонического
JSON для проверки целостности. Это **не цифровая подпись**: достоверность чтения
основана на проверенном SSH и защищённом состоянии root.

Если запись completion не удалась, но systemd подтверждает нормальный выход
наблюдателя с кодом 0 при совпадающем InvocationID, возвращается
`state=succeeded`, `exit_code=0`, `accounting_status=failed`. Это потеря учёта,
а не основание повторить команду. Для аварийного завершения наблюдателя,
ненулевого исхода без сохранённого свидетельства либо исчезновения unit
возвращается `unknown`: ошибка Python-наблюдателя не считается кодом команды.

| Событие | Поведение |
| --- | --- |
| Потеря ответа `start` | UUID уже известен; читать `status` для него, не повторять `start` |
| Обрыв SSH | Служба systemd продолжает работу; после восстановления обновить точное ожидание транспорта и прочитать старое задание |
| Остановка/перезапуск локального daemon | Служба продолжается; заново разрешить sudo и обновить ожидание нового экземпляра daemon |
| Перезагрузка удалённого узла | Сохранённое completion остаётся доказательством; незавершённое задание становится `unknown` и само не возобновляется |
| Истечение `wait --timeout` | Клиент завершается с 124; удалённое задание не получает сигнал |
| Неожиданное исчезновение unit | Без completion — `unknown`; автоматического восстановления службы нет |

Короткое управление имеет собственный предел ожидания ответа. Удалённого
ограничения времени жизни в этой версии нет. Это сознательно исключает убийство
apt/dpkg по локальному таймауту.

`stop` проверяет UUID, транзакцию, hash команды, цель, boot ID и InvocationID,
затем отправляет только SIGTERM всей группе службы. Наблюдатель сохраняет
возможный код завершения. Игнорирующее TERM задание остаётся работающим;
параметра `--force`, автоматического SIGKILL и повторного запуска нет.
Остановка пакетного менеджера может оставить недонастроенные пакеты. После неё
нужны проверка `dpkg --audit` и отдельное согласованное восстановление.

## Объём и очистка

Каждый поток stdout/stderr сохраняет первые 1 МиБ, затем вывод продолжает
считываться и отбрасываться. Счётчики фиксируют усечение. `tail` читает максимум
64 КиБ одного потока; не нужно скачивать весь журнал. Максимум — 256 заданий,
после чего новый запуск отклоняется. Файлы входа и метаданных также ограничены.

Автоматической очистки нет: активное задание или единственное свидетельство
неизвестного исхода никогда не удаляется. Архивирование и освобождение места
администратором требуют предварительного разбора всех `unknown`. Этот выпуск
не предлагает агенту обходить ограничение удалением root-каталогов.

## Граница agent-safe и opencode_permissions

Проверено: agent-safe `master@cc48985ec047114939d0bc5a684ebd10b04c67bd`
поддерживает короткий `ssh_relay_risky`; его тесты требуют receipt короткой
операции и отдельную проверку состояния. Длительное `sudo-job` к этому адаптеру
пока не подключено. Нельзя передавать новый JSON старому адаптеру как будто
это `exec --json --risky`.

Будущий отдельный адаптер должен:

1. До запуска согласовать точные байты команды, SSH-цель, UUID и ожидаемые
   изменения существующим механизмом разрешений, затем сохранить их в журнале.
2. Отметить `running` как начатую незавершённую операцию. Receipt короткого
   `systemd-run` не завершает транзакцию.
3. При `unknown` сохранить блокировку повторного исполнения и выполнять только
   согласованное чтение `status`/`tail`. Обновление ожидания после reconnect
   не даёт разрешения на новую мутацию.
4. Принять completion только при совпадающих UUID, цели, hash команды и
   целостности свидетельства; дополнительно проверить фактическое состояние.
5. Разделять успешную команду и отказ учёта; не повторять установку после
   `accounting_status=failed`.
6. Согласовывать `stop`, восстановление и откат как отдельные операции.

Параметр `--approved` в ssh_relay не вводится. Права человека, оценка риска и
откат остаются за соседними инструментами. Для их согласования подготовлено
описание интерфейса; совместная исполняемая интеграция — отдельная приёмка.

## Выпуск и оставшиеся проверки

Добавлены модульные проверки протокола/подмен и отдельный процесс GitHub Actions
с настоящими SSH, sudo с паролем, systemd, установкой `hello`, проверкой
`dpkg --audit`, кодом 7, ограничением вывода, потерей ответа, перезапуском daemon
и мягкой остановкой на одноразовых Ubuntu 22.04/24.04.

Локальная среда этого диалога не имеет systemd как PID 1. Старые тесты управления
процессами также не проходят в ней на неизменённой базе; результат полного
местного прогона не объявляется успешным. Итоговые проверки GitHub относятся
к конкретному SHA PR и записываются в его описании.

На текущем кандидате автоматическая приёмка уже подтверждает настоящий
Windows-клиент → Ubuntu 22.04/24.04, программную перезагрузку и аппаратный сброс
гостя, а также отказ записи через отдельный заполненный tmpfs. Фактические
результаты и точный SHA фиксируются в описании PR.

До поддерживаемого выпуска остаётся совместная исполняемая интеграция
agent-safe/opencode_permissions с новым жизненным циклом. Пока она не
подтверждена, кандидат не объявляется готовым для установки на пользовательские
VPS и #52 не закрывается.

При обновлении нужны клиент и daemon одной сборки, остановка старого daemon
и ручной запуск нового с обоими разрешающими параметрами. Это не останавливает
уже запущенные службы root; их нужно проверить по сохранённым UUID и hash.


## Автоматическая приёмка без пользовательских VPS

Дополнительные испытания выполняются в GitHub Actions, без настройки v2/v3/v6/vserv
и без пользовательских паролей. Linux-набор дополнен конкурентным резервированием
через независимые SSH-соединения, запретом изменения root-файлов обычным пользователем,
повреждением/символической ссылкой completion и настоящим ENOSPC на tmpfs размером
1 МиБ. Заполняется только этот временный раздел; полезная команда не использует apt.

Отдельные задания Windows Server 2022 запускают настоящие Ubuntu 22.04 (jammy)
и 24.04 (noble) в QEMU TCG. Windows-клиент и daemon находятся вне гостевой Ubuntu.
Это SSH до отдельной ОС с собственным ядром и systemd, а не подмена команд или
SSH-сервер на Windows. QEMU устанавливается только для CI, контрольная сумма
установщика закреплена; образ Ubuntu сверяется с официальным SHA256SUMS.
Ключ гостевой машины создаётся стендом заранее и используется в known_hosts;
проверка ключа SSH не отключается. Искусственные учётные записи удаляются вместе
с одноразовой машиной. Испытательная подстановка getpass запрещена вне Actions.

Windows выполняет тот же сквозной набор, отдельный вызов публичного CLI и короткий
wait, программную перезагрузку гостя и аппаратный сброс QEMU. Завершённое
свидетельство должно сохраняться; прерванное при сбросе задание остаётся unknown,
не возобновляется и не повторяется. Перезапускается только гость, не машина Actions.
Две попытки конкурентного start должны дать ровно одно полезное исполнение.
Отчёт содержит SHA исходников, ОС, число проверок и результат; session-файлы,
ключи, образ, cloud-init и необработанная консоль гостя не публикуются.

Добавление workflow не доказывает прохождение: результат фиксируется в PR по
актуальному HEAD после реального прогона. Совместная исполняемая интеграция
agent-safe/opencode_permissions остаётся отдельным условием выпуска.
