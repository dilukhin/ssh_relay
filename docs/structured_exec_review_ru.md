# Структурированный exec: оценка необходимости и следующий этап

Дата: 2026-09-19. Задача: [#47](https://github.com/dilukhin/ssh_relay/issues/47).

Статус: **проектное предложение для согласования; новый интерфейс исполнения не реализован**.

## 1. Решение

На текущем этапе сохранить строковый API ssh_relay. **Отложить удалённый помощник и RemoteProcessSpec**, пока agent-safe#25 не задаст конкретный структурированный вход и корпус сценариев, которым недостаточно существующих средств. Отдельные exec-script/sudo-exec-script не возвращать.

Первый следующий шаг — локальный ProcessSpec в agent-safe, прежде всего для verify/rollback/receipt, и совместная проверка его полей с opencode_permissions#34. Это устраняет доказанный строковый разбор у потребителя без обязательного изменения relay. Удалённую часть можно отложить независимо от локальной.

Для существующих коротких shell-команд использовать нынешний exec. Передавать готовую строку одним аргументом локальному процессу, без лишней оболочки. При необходимости точного многострочного файла рассматривать имеющийся upload + явный exec как отдельную процедуру с собственной проверкой и очисткой. Это не универсальное решение для секретов или risky-квитанций.

Новая опция --command-file — резервный узкий кандидат, если Windows-проверка подтвердит повреждение/ограничение именно локальной передачи command string. Она не становится RemoteProcessSpec и не устраняет удалённую оболочку. Сейчас её реализация не обоснована измерениями на Windows.

## 3. Где возникают ошибки

Нужно различать три границы:

1. Агент/терминал → локальный argv ssh_relay. Ручные cmd.exe/PowerShell и запуск subprocess списком имеют разные правила. Корректность одного пути не доказывает другой.
2. command string → JSON → SSH exec. JSON сохраняет строковое значение, но не превращает его в удалённый argv. После авторизации важно использовать тот же неизменяемый текст, а не заново собирать похожую команду.
3. Удалённая оболочка → аргументы программы. Пробелы, кавычки, $, обратные косые черты, пустые аргументы и переводы строки имеют семантику оболочки. Для sudo добавляется явный sh -c; корректная упаковка этой строки не исправляет неверно составленную внутреннюю команду.

На текущем main execute_remote_command передаёт stdin_data до цикла чтения вывода. Поэтому нельзя открыть публичную передачу большого stdin, просто добавив поле JSON: нужны отдельные ограничения и одновременное чтение/запись без зависания. Общий MAX_MESSAGE_SIZE=96 МиБ не является разумным бюджетом структурированного запроса. Существующие пределы короткого exec — 4 МиБ вывода и стандартный command timeout 120 секунд; новые контракты не должны молча их расширять.

## 4. Сравнение вариантов

| Вариант | Что решает | Ограничения и новые обязательства | Решение сейчас |
| --- | --- | --- | --- |
| Существующий exec; готовая строка одним локальным аргументом | Убирает лишнюю локальную оболочку в программном вызове | Удалённая shell-семантика остаётся; корректное составление строки и её анализ обязательны | Сохранить |
| --command-file с точным UTF-8 содержимым | Убирает текст команды из локального argv и часть ручного экранирования | Нужны лимит, строгий decode, запрет NUL, точные правила BOM/CRLF без молчаливой нормализации, одно чтение и binding проверенного содержимого; удалённая shell остаётся | Только после доказанного локального сценария |
| upload + короткий exec | Уже позволяет передать файл отдельно от строки запуска | Два действия, целевой путь, права, подмена файла, срок хранения и очистка после unknown; текущий receipt хеширует строку запуска, а не содержимое скрипта | Допустимая явная процедура для подходящего сценария, не общий structured endpoint |
| Фиксированный удалённый помощник + ProcessSpec | Может принять argv/stdin как данные и вызвать процесс без динамического shell text | Доверенная установка, версии, runtime, host/helper identity, framing, лимиты, исход запуска и права sudo; нет готовой инфраструктуры помощника | Отложить |

Допустима детерминированная POSIX-сериализация для **существующего shell workload**, если анализируется и связывается именно эта командная строка. Нельзя принять новый запрос с обещанием shell=false, молча сериализовать его в строку и объявить выполненным как структурированный argv.

## 5. Синтетическая проверка

В текущей Linux-среде, Python 3.12, выполнена локальная проверка восьми классов аргументов. Приёмник — временный Python-файл, печатающий JSON от sys.argv[1:]. Сравнивались subprocess со списком аргументов, /bin/sh -c с shlex.join и наивная конкатенация аргументов пробелами. Все данные искусственные; SSH, пользовательские сессии и sudo не использовались.

| Класс | Прямой argv | POSIX shlex.join | Наивная склейка |
| --- | --- | --- | --- |
| Пробелы | Точно | Точно | Искажён |
| Одинарные/двойные кавычки | Точно | Точно | Искажён/ошибка shell |
| Unicode | Точно | Точно | Точно |
| Пустой аргумент | Точно | Точно | Потерян |
| JSON как один аргумент | Точно | Точно | Искажён |
| Литеральные $ и $(...) | Точно | Точно | Интерпретированы |
| Перевод строки внутри аргумента | Точно | Точно | Искажён/дополнительная команда |
| Обратные косые черты | Точно | Точно | Искажён |

Результат: 8/8 для прямого argv, 8/8 для корректной POSIX-сериализации, 1/8 для наивной склейки. Это подтверждает полезность точного представления аргументов, но **не доказывает необходимость удалённого помощника**. Не проверены реальные Windows argv, cmd.exe/PowerShell, SSH-сервер, пользовательский stdin и sudo. Процедуры command-file/upload/helper сравнены архитектурно, а не выданы за существующие реализации.

Небольшой воспроизводимый стенд приведён в конце документа.

## 6. Сопоставление с владельцами контрактов

Имена ниже логические, не утверждённая схема JSON.

| Данные | Владелец/граница | Требование к будущему remote-профилю |
| --- | --- | --- |
| program, argv, cwd | agent-safe producer + доверенный исполнитель | Уточнить argv[0]; сохранить порядок, пустые элементы, точное значение и выбранный executable/cwd |
| env | Producer объявляет зависимости; opencode_permissions связывает значимые факты | Не пересылать полное окружение; неизвестные значимые поля не игнорировать |
| stdin / script | Producer и исполнитель | Ограниченные точные bytes; отсутствие stdin и пустой stdin различать, если это влияет на результат |
| Session, endpoint, host key, SSH user | relay/SSH transport | Имя сессии и host-label не являются доказанной идентичностью узла; нужен факт от аутентифицированного транспорта и согласованное связывание с авторизацией |
| Helper path/version/runtime | Доверенный процесс установки + transport | Фиксированный bootstrap, права и проверка версии; произвольный путь от вызывающего не становится доверенным |
| targets/effects/ALLOW | opencode_permissions | Подтверждает существующий анализатор, не модельные заявления или approved=true |
| Timeout/output/input limits | relay + consumer | Ограничения действуют до чтения/передачи; timeout после возможного запуска не означает not_started |
| transaction_id/receipt_id/request_id | Существующие владельцы correlation | Разные назначения; ни один ID не разрешает повтор действия |
| Проверка результата/recovery | agent-safe | Relay сообщает исход, не выбирает rollback и не повторяет risky-команду |

Предварительное сопоставление opencode_permissions PR #36 совместимо с этим выбором **на уровне границ**: remote slice отложен, новая схема не зафиксирована. Это не финальное межпроектное согласование. _process_operation не переносит произвольные stdin/env/helper в identity; такой вход нельзя объявить parsed-simple/v1 с parser.status=exact. Неизвестные существенные поля требуют отказа/не-ALLOW по действующим правилам.

## 7. Если помощник всё-таки потребуется

До разрешения реализации отдельный документ должен закрыть следующие вопросы:

1. Конкретный потребитель и минимальная неизменяемая схема, включая точное значение executable/argv[0], cwd, declared env, режим и лимит stdin. Не обещать общий произвольный script executor.
2. Linux-target и доступность runtime: Python на сервере сейчас не требуется самим relay, нельзя предполагать его установленным. Установка помощника — отдельное управляемое действие, не автоматическая побочная операция exec.
3. Доверенные path/owner/permissions/version, запрет подмены помощника и значимого payload между разрешением и исполнением. Фиксированный SSH bootstrap допустим; динамические argv должны оставаться данными.
4. Отдельный bounded framing для control/result и stdout/stderr. Не интерпретировать строку пользовательского вывода как подтверждение «не запущено». Одновременный ввод/вывод, общий deadline, лимиты request/stdin/output и ограниченное потребление RAM.
5. Capability с явной версией. Старый daemon, отсутствующий helper, неизвестная версия — отказ structured-запросу без тихого перехода к строковому API. Старые exec/sudo-exec продолжают работать как раньше.
6. Sudo исключить из первого возможного MVP: сейчас stdin занят передачей пароля. Для последующего расширения отдельно определить framing пользовательского stdin, область повышения прав, доверенность помощника и запрет утечки пароля.
7. Versioned execution payload digest, связанный с фактическими bytes и transaction/receipt. Не менять значение legacy command_hash. Digest — не разрешение, не идемпотентность и не безопасная замена низкоэнтропийному секрету. Запрет payload/argv/stdin/secrets в диагностических журналах.

### Машинные исходы

| Событие | Требуемый смысл |
| --- | --- |
| Локальная валидация/нет capability до отправки операции | not_started, код 10 |
| Достоверный связанный с запросом отказ доверенного помощника до spawn | not_started, код 10 |
| Разрыв после возможной доставки, нет подтверждённого результата | unknown, код 13; отсутствие start-ack не доказывает отсутствие запуска |
| Подтверждённое завершение с ненулевым кодом | command_failed, код 11 |
| Команда успешна, обязательная квитанция не подтверждена | partial_success, код 12 |
| Подтверждены команда и требуемая квитанция | succeeded, код 0 |

Новый локальный replay не меняет эти исходы. Нельзя автоматически повторять запрос ради квитанции, start-ack, связи или лучшего декодирования.

## 8. Минимальный план и критерии возврата

1. Завершить #44/PR #46 и #45/PR #48 в принятом порядке; этот документ не блокирует их и не расширяет их объём.
2. Получить конкретный draft agent-safe#25: структура входа, способ запуска CLI/API, verify/rollback/receipt, ответственность за повторную проверку перед выполнением.
3. До окончательной схемы сверить draft с opencode_permissions#34/PR #36. На текущем этапе выбрать локальный путь; не добавлять remote env/stdin/helper только ради полноты схемы.
4. Если есть реальные ошибки удалённого вызова, воспроизвести их на Windows-клиенте через установленный CLI и точный SHA: отдельно cmd.exe, PowerShell и программный argv. Сначала короткие безопасные команды и искусственные данные; production-команду ради проверки не повторять.
5. Если сбой только на локальной границе command string — узкий design --command-file, без нового daemon endpoint. Если требуются именно remote argv/stdin и существующий shell workload неприемлем — вернуться к помощнику по §7.
6. При выборе реализации: отдельный PR после согласования; проверить пробелы/кавычки/Unicode/пустой argv/JSON/newline stdin/non-zero exit, missing helper/version mismatch, разрыв до/после возможного запуска, risky receipt и unknown без retry. Старые text/JSON/replay contracts должны сохраниться.

Итог этой итерации: **defer remote structured implementation; сохранить существующий API; сначала конкретизировать локального потребителя**. #47 не закрывается автоматически этим предложением: остаются согласование выбора и конкретного следующего этапа с draft agent-safe#25. Закрытие #27/#28 не объявляется реализацией их первоначальных идей.

## 9. Воспроизведение локального опыта

Сохранить следующий блок в отдельный временный .py и запустить Python 3.12 на Linux. Он создаёт только временный файл, не обращается к SSH, не читает пользовательские секреты и не требует сторонних зависимостей. Результат по каждому классу сравнивается с исходным массивом.

```python
"""Локальная синтетическая проверка передачи аргументов; SSH не используется."""
import json
import os
from pathlib import Path
import shlex
import subprocess
import sys
import tempfile

cases = {
    "spaces": ["два слова", "a b"],
    "quotes": ['a"b', "a'b"],
    "unicode": ["Привет", "ёж"],
    "empty": ["", "after"],
    "json": ['{"text":"a b","n":1}'],
    "literal_dollar": ["$DEMO_VALUE", "$(printf expanded)"],
    "newline": ["line1\nline2"],
    "backslash": [r"C:\folder\file", "end\\"],
}
with tempfile.TemporaryDirectory() as directory:
    echo = Path(directory) / "echo_args.py"
    echo.write_text("import json,sys; print(json.dumps(sys.argv[1:],ensure_ascii=False))\n", encoding="utf-8")
    prefix = [sys.executable, str(echo)]
    environment = {"PATH": os.defpath, "DEMO_VALUE": "expanded", "PYTHONIOENCODING": "utf-8"}
    result = []
    for name, args in cases.items():
        commands = {
            "direct_argv": prefix + args,
            "posix_quoted": ["/bin/sh", "-c", shlex.join(prefix + args)],
            "naive_join": ["/bin/sh", "-c", shlex.join(prefix) + " " + " ".join(args)],
        }
        row = {"case": name}
        for method, command in commands.items():
            process = subprocess.run(command, capture_output=True, text=True, encoding="utf-8", env=environment, timeout=5)
            try:
                value = json.loads(process.stdout)
            except (ValueError, UnicodeError):
                value = None
            row[method] = process.returncode == 0 and value == args
        result.append(row)
    print(json.dumps(result, ensure_ascii=False, indent=2))
```
