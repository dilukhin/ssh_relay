# Структурированный exec: оценка необходимости и следующий этап

Дата: 2026-09-19. Задача: [#47](https://github.com/dilukhin/ssh_relay/issues/47).

Статус: **архитектурное решение завершено: реализацию RemoteProcessSpec и удалённого помощника отложить; существующий строковый API сохранить**. Решение оформлено для принятия в PR #49; новый интерфейс исполнения не реализован.

## 1. Решение

**Решение: отложить реализацию RemoteProcessSpec и удалённого помощника; сохранить строковый exec/sudo-exec без новых команд, возможностей протокола и зависимостей.** В проверенном наборе источников не найден конкретный удалённый потребитель с доказанно недостаточным существующим API. Это вывод о нынешнем объёме работ, а не доказательство универсальной достаточности shell exec.

agent-safe#28/#31 уже слиты: локальный ProcessSpec существует в master и не требует SSH. Формулировка «ждём локальный проект интерфейса» больше не применяется. Само наличие локального ProcessSpec, его публичных входов или готового адаптера разрешений не является условием автоматического возобновления удалённой реализации. Отдельные exec-script/sudo-exec-script не возвращать.

Первый следующий шаг — связать внутренние локальные recover и их verify из agent-safe#31 с opencode_permissions#34; публичные verify/receipt/main-spec остаются отдельной частью agent-safe#25A. Публичные структурированные входы затем устранят доказанный строковый разбор у потребителя без обязательного изменения relay. Удалённую часть можно отложить независимо от локальной.

Для существующих коротких shell-команд использовать нынешний exec. Передавать готовую строку одним аргументом локальному процессу, без лишней оболочки. При необходимости точного многострочного файла рассматривать имеющийся upload + явный exec как отдельную процедуру с собственной проверкой и очисткой. Это не универсальное решение для секретов или risky-квитанций.

Новая опция --command-file — резервный узкий кандидат, если Windows-проверка подтвердит повреждение/ограничение именно локальной передачи command string. Она не становится RemoteProcessSpec и не устраняет удалённую оболочку. Сейчас её реализация не обоснована измерениями на Windows.

## 3. Где возникают ошибки

Нужно различать три границы:

1. Агент/терминал → локальный argv ssh_relay. Ручные cmd.exe/PowerShell и запуск subprocess списком имеют разные правила. Корректность одного пути не доказывает другой.
2. command string → JSON → SSH exec. JSON сохраняет строковое значение, но не превращает его в удалённый argv. После авторизации важно использовать тот же неизменяемый текст, а не заново собирать похожую команду.
3. Удалённая оболочка → аргументы программы. Пробелы, кавычки, $, обратные косые черты, пустые аргументы и переводы строки имеют семантику оболочки. Для sudo добавляется явный sh -c; корректная упаковка этой строки не исправляет неверно составленную внутреннюю команду.

На текущем main execute_remote_command передаёт stdin_data до цикла чтения вывода. Поэтому нельзя открыть публичную передачу большого stdin, просто добавив поле JSON: нужны отдельные ограничения и одновременное чтение/запись без зависания. Общий MAX_MESSAGE_SIZE=96 МиБ не является разумным бюджетом структурированного запроса. Существующие пределы короткого exec — 4 МиБ вывода и стандартный command timeout 120 секунд; новые контракты не должны молча их расширять.

## 4. Сравнение вариантов

| Вариант | Что решает | Ограничения и новые обязательства | Решение сейчас |
| --- | --- | --- | --- |
| Существующий exec; готовая строка одним локальным аргументом | Убирает лишнюю локальную оболочку в программном вызове | Удалённая shell-семантика остаётся; корректное составление строки и её анализ обязательны | Сохранить |
| --command-file с точным UTF-8 содержимым | Убирает текст команды из локального argv и часть ручного экранирования | Нужны лимит, строгий decode, запрет NUL, точные правила BOM/CRLF без молчаливой нормализации, одно чтение и binding проверенного содержимого; удалённая shell остаётся | Только после доказанного локального сценария |
| upload + короткий exec | Уже позволяет передать файл отдельно от строки запуска | Два действия, целевой путь, права, подмена файла, срок хранения и очистка после unknown; текущий receipt хеширует строку запуска, а не содержимое скрипта | Допустимая явная процедура для подходящего сценария, не общий structured endpoint |
| Фиксированный удалённый помощник + ProcessSpec | Может принять argv/stdin как данные и вызвать процесс без динамического shell text | Доверенная установка, версии, runtime, host/helper identity, framing, лимиты, исход запуска и права sudo; нет готовой инфраструктуры помощника | Отложить |

Допустима детерминированная POSIX-сериализация для **существующего shell workload**, если анализируется и связывается именно эта командная строка. Нельзя принять новый запрос с обещанием shell=false, молча сериализовать его в строку и объявить выполненным как структурированный argv.

## 5. Синтетическая проверка

В текущей Linux-среде, Python 3.12, выполнена локальная проверка восьми классов аргументов. Приёмник — временный Python-файл, печатающий JSON от sys.argv[1:]. Сравнивались subprocess со списком аргументов, /bin/sh -c с shlex.join и наивная конкатенация аргументов пробелами. Все данные искусственные; SSH, пользовательские сессии и sudo не использовались.

| Класс | Прямой argv | POSIX shlex.join | Наивная склейка |
| --- | --- | --- | --- |
| Пробелы | Точно | Точно | Искажён |
| Одинарные/двойные кавычки | Точно | Точно | Искажён/ошибка shell |
| Unicode | Точно | Точно | Точно |
| Пустой аргумент | Точно | Точно | Потерян |
| JSON как один аргумент | Точно | Точно | Искажён |
| Литеральные $ и $(...) | Точно | Точно | Интерпретированы |
| Перевод строки внутри аргумента | Точно | Точно | Искажён/дополнительная команда |
| Обратные косые черты | Точно | Точно | Искажён |

Результат: 8/8 для прямого argv, 8/8 для корректной POSIX-сериализации, 1/8 для наивной склейки. Это подтверждает полезность точного представления аргументов, но **не доказывает необходимость удалённого помощника**. Не проверены реальные Windows argv, cmd.exe/PowerShell, SSH-сервер, пользовательский stdin и sudo. Процедуры command-file/upload/helper сравнены архитектурно, а не выданы за существующие реализации.

Небольшой воспроизводимый стенд приведён в конце документа.

## 6. Сопоставление с владельцами контрактов

Имена ниже логические, не утверждённая схема JSON.

| Данные | Владелец/граница | Требование к будущему remote-профилю |
| --- | --- | --- |
| program, argv, cwd | agent-safe producer + доверенный исполнитель | Локальный argv не содержит program; после раскрытия ссылок на артефакты проекция использует [program, *resolved_argv] ровно один раз. Удалённая схема отдельно не утверждена |
| env | Producer объявляет зависимости; opencode_permissions связывает значимые факты | Не пересылать полное окружение; неизвестные значимые поля не игнорировать |
| stdin / script | Producer и исполнитель | Ограниченные точные bytes; отсутствие stdin и пустой stdin различать, если это влияет на результат |
| Session, endpoint, host key, SSH user | relay/SSH transport | Имя сессии и host-label не являются доказанной идентичностью узла; нужен факт от аутентифицированного транспорта и согласованное связывание с авторизацией |
| Helper path/version/runtime | Доверенный процесс установки + transport | Фиксированный bootstrap, права и проверка версии; произвольный путь от вызывающего не становится доверенным |
| targets/effects/ALLOW | opencode_permissions | Подтверждает существующий анализатор, не модельные заявления или approved=true |
| Timeout/output/input limits | relay + consumer | Ограничения действуют до чтения/передачи; timeout после возможного запуска не означает not_started |
| transaction_id/receipt_id/request_id | Существующие владельцы correlation | Разные назначения; ни один ID не разрешает повтор действия |
| Проверка результата/recovery | agent-safe | Relay сообщает исход, не выбирает rollback и не повторяет risky-команду |

Обновлённое сопоставление opencode_permissions PR #36 и принятый локальный вариант agent-safe#28 совместимы с этим выбором: удалённый этап отложен, локальное согласование не ждёт relay. Это подтверждённая совместимость архитектурных границ; готовность адаптера разрешений и совместные проверки исполнения пока не подтверждены. _process_operation не переносит произвольные stdin/env/helper в identity; такой вход нельзя объявить parsed-simple/v1 с parser.status=exact. Неизвестные существенные поля требуют отказа/не-ALLOW по действующим правилам.

### 6.2. Предлагаемые решения для следующего локального этапа

Эти пункты относятся только к локальной интеграции agent-safe#25A / opencode_permissions#34. Они не являются условиями завершения #47, принятия/слияния #49 или автоматического запуска удалённой разработки. Готовность локального адаптера подтверждается в соответствующих проектах; ssh_relay не присваивает себе право утверждать их окончательную схему.

| Вопрос | Предлагаемое решение | Владелец и критерий приёмки |
| --- | --- | --- |
| Что именно разрешается | После load_bundle и resolved_spec подготовить неизменяемые факты конкретной роли. Привязать решение к одному вызову; непосредственно перед каждым spawn повторно проверить факты. Recover и verify имеют отдельные привязки; разрешение исходной mutation не наследуется | agent-safe предоставляет факты и проверяет исполнение; opencode_permissions владеет решением и связью с вызовом. Подмена spec/артефакта/роли и повтор чужого разрешения должны остановиться до spawn |
| Идентичность файлов | Использовать профиль с явной версией и именованными stat-компонентами; большие целые передавать точными десятичными строками. Точную кодировку строки object_identity зафиксировать в адаптере; не менять op-jcs-v1 и не округлять наносекунды | opencode_permissions#34 совместно с resolver agent-safe: одинаковые факты дают одинаковую identity; изменение любого значимого компонента даёт другую. | Артефакты, timeout, env | После раскрытия ссылок связывать сохранённый путь, ID, размер и digest каждого значимого артефакта, mode/content stdin и целый timeout. Неподдерживаемые env/секретные/удалённые поля отклонять явно | opencode_permissions#34 определяет строгий профиль, agent-safe повторно проверяет использованные копии. Декларация non_secret:true, shell=false, Python -I и пустой env_dependencies не доказывают безопасность скрипта |

Digest идентифицирует данные, но не выдаёт разрешение и не разрешает повтор. Неизвестные эффекты остаются non-ALLOW; native DENY/ASK и действующий P0 не расширяются. Выбор точных UTF-8 bytes относится к новому structured-пути и не меняет прежний строковый CLI.

**Результат для ssh_relay:** текущему локальному потребителю не нужны новые команды или capability. Блокирующей зависимости локального этапа от #47 нет. Удалённый ProcessSpec нельзя выдавать за реализованный или передавать через тихую сборку shell string.

## 7. Обязательные требования при возврате к удалённому помощнику

Ниже требования к будущему проекту после выполнения условий §8; это не утверждённая схема и не уже существующие возможности. До разрешения реализации отдельный документ должен закрыть следующие вопросы:

1. Конкретный потребитель и минимальная неизменяемая схема, включая точное значение executable/argv[0], cwd, declared env, режим и лимит stdin. Не обещать общий произвольный script executor.
2. Linux-target и доступность runtime: Python на сервере сейчас не требуется самим relay, нельзя предполагать его установленным. Установка помощника — отдельное управляемое действие, не автоматическая побочная операция exec.
3. Доверенные path/owner/permissions/version, запрет подмены помощника и значимого payload между разрешением и исполнением. Фиксированный SSH bootstrap допустим; динамические argv должны оставаться данными. Источник идентичности узла — проверенный host key установленного аутентифицированного SSH-транспорта и его подтверждённая привязка к разрешённому узлу; имя сессии, host_label и строковые host/port/user сами по себе этого не доказывают. Проект должен определить получение этого факта, проверку после reconnect и состав значимых параметров маршрута: конечный узел/порт/пользователь, целевой контекст прав, посредник или proxy при их поддержке. Неподдерживаемый маршрут отклоняется; изменение связанного контекста отменяет прежнее разрешение. Нынешний session/endpoint JSON не объявляется готовым источником всех этих подтверждённых фактов.
4. Отдельный bounded framing для control/result и stdout/stderr. Не интерпретировать строку пользовательского вывода как подтверждение «не запущено». Одновременный ввод/вывод, общий deadline, лимиты request/stdin/output и ограниченное потребление RAM.
5. Capability с явной версией. Старый daemon, отсутствующий helper, неизвестная версия — отказ structured-запросу без тихого перехода к строковому API. Старые exec/sudo-exec продолжают работать как раньше.
6. Sudo исключить из первого возможного MVP: сейчас stdin занят передачей пароля. Для последующего расширения отдельно определить framing пользовательского stdin, область повышения прав, доверенность помощника и запрет утечки пароля.
7. Versioned execution payload digest, связанный с фактическими bytes и transaction/receipt. Не менять значение legacy command_hash. Digest — не разрешение, не идемпотентность и не безопасная замена низкоэнтропийному секрету. Запрет payload/argv/stdin/secrets в диагностических журналах.

### Машинные исходы

| Событие | Требуемый смысл |
| --- | --- |
| Локальная валидация/нет capability до отправки операции | not_started, код 10 |
| Достоверный связанный с запросом отказ доверенного помощника до spawn | not_started, код 10 |
| Разрыв после возможной доставки, нет подтверждённого результата | unknown, код 13; отсутствие start-ack не доказывает отсутствие запуска |
| Подтверждённое завершение с ненулевым кодом | command_failed, код 11 |
| Команда успешна, обязательная квитанция не подтверждена | partial_success, код 12 |
| Подтверждены команда и требуемая квитанция | succeeded, код 0 |

Новый локальный replay не меняет эти исходы. Нельзя автоматически повторять запрос ради квитанции, start-ack, связи или лучшего декодирования.

## 8. Условия возобновления и завершение архитектурного этапа

### 8.1. Когда возвращаться к проектированию

До появления условий ниже реализация отложена без календарного срока. Завершение локальных #25A/#34 само по себе не снимает отсрочку.

1. **Назван реальный удалённый потребитель.** В новой или переоткрытой связанной задаче указаны проект-владелец, конкретное действие и ожидаемый результат, Windows-клиент/Linux-цель, требуемые program/argv/cwd, режим stdin, необходимость sudo и допустимые эффекты. Одного пожелания «нужен ProcessSpec по SSH» недостаточно.
2. **Определена недостаточность существующего API.** Есть воспроизводимый пример на искусственных данных с точными SHA и окружением либо явное требование потребителя «argv без удалённой оболочки»/ограниченного пользовательского stdin, которое текущий API не предоставляет. Для ошибки указывается конкретная граница из §3; гипотезу и наблюдение разделяют. Нельзя повторять рабочую команду с неизвестным исходом ради доказательства.
3. **Проверено минимальное средство исправления.** Сравнены прямой локальный запуск argv, корректная передача существующей command string, при допустимости shell — её точная POSIX-сериализация, и отдельная процедура upload + проверяемый запуск. Письменно указано, почему подходящие варианты не удовлетворяют сценарию. Upload + shell exec никогда не считается эквивалентом удалённого argv без оболочки.
4. **Определены владельцы следующего этапа.** Потребитель подтверждает необходимость удалённого пути; ssh_relay владеет транспортом/исходами, opencode_permissions — разрешением/привязкой. Создаётся отдельная задача проектирования с ограниченной проверкой на временных целях, без автоматической установки помощника.

Эти условия открывают проектирование, а не автоматически разрешают реализацию или развёртывание.

### 8.2. Как выбрать следующий вид работы

| Подтверждённая причина | Следующий шаг |
| --- | --- |
| Ошибка только на границе терминал → локальный argv | Исправить способ программного вызова/экранирования. --command-file рассматривать только если минимальное воспроизведение на установленном CLI подтверждает оставшееся повреждение или практический предел длины |
| Требуется --command-file | Отдельная узкая задача: exact UTF-8, BOM/CRLF/NUL, лимит, однократное чтение и привязка проверенного текста; без нового daemon endpoint и без обещания shell=false |
| Получена правильная command string, но ошибка удалённого shell-разбора | Исправить явную shell-программу/сериализацию, если потребитель допускает shell. Не лечить её локальной command-file опцией |
| Потребителю необходимы именно удалённый argv без shell или пользовательский stdin, и существующие средства неприемлемы | Конкретный проект по §7, затем отдельная задача реализации после оценки угроз и совместимости |
| Ошибка endpoint/разрешения/квитанции | Исправить соответствующий контракт владельца; сама по себе такая ошибка не обосновывает передачу нового ProcessSpec |

Для подтверждения ошибки локальной передачи нужны Windows-результаты отдельно для cmd.exe, PowerShell и программного argv, если эти способы входят в сценарий. Для вывода о передаче по SSH/удалённой оболочке нужен настоящий SSH-прогон на разрешённой временной цели; локальная имитация его не заменяет.

### 8.3. Условия реализации после нового проектирования

Проект должен закрыть §7: версии/capability, точную границу данных исполнения, подтверждённые host/route/helper facts, привязку разрешения к payload, лимиты и одновременную передачу ввода/вывода, а также явный отказ при отсутствии помощника или несовместимой версии без перехода к shell string. Sudo исключается из первого объёма, если разделение пароля и пользовательского stdin не согласовано отдельно.

Будущая задача реализации включает проверки Windows-клиент → настоящий Linux SSH: пробелы/кавычки/Unicode/пустые аргументы/JSON, LF/CRLF/пустой stdin и отсутствие stdin, ненулевой exit, отсутствие помощника и несовместимость версии, смену host/маршрута, разрыв до и после возможной доставки, risky receipt, unknown без повтора и неизменность старых text/JSON/replay-контрактов. Синтетические сбои и реальные прогоны учитываются раздельно.

## 9. Воспроизведение локального опыта

Сохранить следующий блок в отдельный временный .py и запустить Python 3.12 на Linux. Он создаёт только временный файл, не обращается к SSH, не читает пользовательские секреты и не требует сторонних зависимостей. Результат по каждому классу сравнивается с исходным массивом.

```python
"""Локальная синтетическая проверка передачи аргументов; SSH не используется."""
import json
import os
from pathlib import Path
import shlex
import subprocess
import sys
import tempfile

cases = {
    "spaces": ["два слова", "a b"],
    "quotes": ['a"b', "a'b"],
    "unicode": ["Привет", "ёж"],
    "empty": ["", "after"],
    "json": ['{"text":"a b","n":1}'],
    "literal_dollar": ["$DEMO_VALUE", "$(printf expanded)"],
    "newline": ["line1\nline2"],
    "backslash": [r"C:\folder\file", "end\\"],
}
with tempfile.TemporaryDirectory() as directory:
    echo = Path(directory) / "echo_args.py"
    echo.write_text("import json,sys; print(json.dumps(sys.argv[1:],ensure_ascii=False))\n", encoding="utf-8")
    prefix = [sys.executable, str(echo)]
    environment = {"PATH": os.defpath, "DEMO_VALUE": "expanded", "PYTHONIOENCODING": "utf-8"}
    result = []
    for name, args in cases.items():
        commands = {
            "direct_argv": prefix + args,
            "posix_quoted": ["/bin/sh", "-c", shlex.join(prefix + args)],
            "naive_join": ["/bin/sh", "-c", shlex.join(prefix) + " " + " ".join(args)],
        }
        row = {"case": name}
        for method, command in commands.items():
            process = subprocess.run(command, capture_output=True, text=True, encoding="utf-8", env=environment, timeout=5)
            try:
                value = json.loads(process.stdout)
            except (ValueError, UnicodeError):
                value = None
            row[method] = process.returncode == 0 and value == args
        result.append(row)
    print(json.dumps(result, ensure_ascii=False, indent=2))
```
