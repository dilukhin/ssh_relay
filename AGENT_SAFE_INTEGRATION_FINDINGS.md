# Findings: интеграция ssh_relay 0.5.1 с agent-safe

Дата наблюдения: 2026-07-23.

Документ описывает практическую интеграцию `ssh_relay` с `agent-safe` при работе с удалёнными Linux/VPS. Android и Termux в этом исследовании не проверялись.

## Контекст

Через именованные relay-сессии выполнялась настройка SSH-доступа на трёх VPS. Требовалось добавить ограниченный публичный ключ пользователю `tunneluser`, сохранив существующие ключи, права и удалённые receipts.

Сессии работали в режиме `--enable-sudo`, потому что целевой `authorized_keys` принадлежал другому пользователю.

## Что подтверждено практической проверкой

- `status --name` подтверждает доступность именованной сессии;
- `exec --name "hostname && whoami && pwd"` позволяет установить идентичность хоста и рабочий контекст;
- `sudo-exec --risky --receipt-path /var/lib/agent-safe/changes.jsonl` выполняет изменение и записывает удалённый receipt;
- stdout, stderr и exit code пригодны для внешней проверки;
- отдельный verify через `sudo-exec` подтверждает содержимое, владельца и режим файла;
- последовательная обработка хостов не создаёт неопределённое состояние остальных сессий при сбое одного узла.

## Подтверждённые ограничения

### 1. Специализированный адаптер agent-safe не поддерживает sudo-exec

Для root-owned target пришлось использовать общий `safe exec-risky` вокруг локального вызова:

```text
py ssh_relay.py sudo-exec --name <name> --risky ...
```

Рабочий обход сохраняет базовый протокол, но теряет часть семантики специализированного relay-adapter.

### 2. Receipts существуют на двух уровнях

В операции участвуют:

- локальный receipt транзакции `agent-safe`;
- удалённый JSONL receipt, записанный `ssh_relay --risky`.

Связь между ними не формализована: нет общего `transaction_id`, удалённого `receipt_id` и проверяемого hash.

### 3. Составная удалённая команда классифицируется как unknown

Идемпотентная операция может включать проверку состояния, изменение, восстановление owner/mode и verify. Наличие `||` и `;` не делает такую операцию автоматически недопустимой, если заданы точный target, expected state, rollback и verify.

Для сложных операций предпочтительнее передавать проверенный скрипт или manifest как единое содержимое с hash, а не наращивать уровни inline quoting.

### 4. Windows quoting ненадёжен для сложных inline-аргументов

На PowerShell 5.1 надёжнее использовать файлы:

```text
--expected-state-file
--rollback-command-file
--verify-command-file
```

Inline JSON, `$()` и вложенные кавычки создают риск неверного разделения аргументов.

### 5. Перед изменением требуется discovery

Read-only проверка должна зафиксировать:

- hostname;
- SSH-пользователя relay;
- cwd;
- целевого пользователя и home;
- режим sudo;
- фактический target path.

### 6. Удалённый receipt сохраняет полную команду

Текущий receipt включает поле `command`. Токен, пароль, приватный URL или другой чувствительный аргумент могут попасть в JSONL.

Безопасный receipt по умолчанию должен хранить hash команды или скрипта и безопасные метаданные. Полную команду допустимо сохранять только отдельным явным режимом после предупреждения.

### 7. Возможен частичный успех

Удалённая команда выполняется раньше записи receipt. Если команда завершилась успешно, а receipt записать не удалось, состояние хоста уже изменено.

Такой результат должен быть машинно различим:

```json
{
  "command_status": "succeeded",
  "receipt_status": "failed",
  "partial_success": true
}
```

Это требует ручной проверки либо rollback из-за потери аудита, а не из-за невыполненной команды.

### 8. Целостность журнала не защищена

Минимально полезная схема:

- `transaction_id`;
- `receipt_id`;
- `previous_receipt_hash`;
- `receipt_hash`;
- устойчивый идентификатор удалённого хоста;
- timestamp UTC.

Цепочка hash не заменяет криптографическую подпись, но позволяет обнаруживать часть случаев удаления, перестановки и подмены записей.

## Разделение задач

### Проект ssh_relay

Задача: [dilukhin/ssh_relay#2](https://github.com/dilukhin/ssh_relay/issues/2).

Отвечает за:

- машиночитаемый JSON-результат risky-операции;
- `transaction_id`, `receipt_id` и hash;
- отдельный `partial_success` при ошибке записи receipt;
- безопасный формат удалённого receipt без полной команды по умолчанию;
- `inspect --json`;
- проектирование `exec-script` и `sudo-exec-script`;
- сохранение семантики stdout, stderr и exit code;
- проверку отсутствия смешения именованных сессий.

Подробный порядок работ приведён в [`SSH_RELAY_CHANGE_PLAN.md`](SSH_RELAY_CHANGE_PLAN.md).

### Проект agent-safe

Задача: [dilukhin/agent-safe#4](https://github.com/dilukhin/agent-safe/issues/4).

Отвечает за:

- режимы адаптера `exec` и `sudo-exec`;
- генерацию локального transaction ID до запуска relay;
- передачу transaction ID в `ssh_relay`;
- разбор JSON-результата relay;
- связь локального receipt с удалённым `receipt_id` и hash;
- различение command failure, verify failure, receipt failure и partial success;
- sudo verify через тот же relay-режим;
- классификацию составных shell-операций;
- expected state, rollback и verify;
- блокировку последующих risky-операций при неопределённом или частично успешном результате.

## Зависимости

1. Сначала в `ssh_relay` фиксируется машинный контракт risky-операции.
2. После стабилизации контракта адаптер `agent-safe` начинает передавать transaction ID и разбирать результат.
3. Команды `inspect` и выполнения скриптов могут добавляться отдельным этапом после P0.
4. Интеграционный тест выполняется только после реализации обеих сторон.

## Критерии интеграционного теста

1. Запустить daemon с `--enable-sudo`.
2. Через `agent-safe` создать root-owned тестовый файл командой `sudo-exec --risky`.
3. Подтвердить локальный и удалённый receipts.
4. Проверить общий transaction ID, remote receipt ID и hash.
5. Проверить owner/mode через sudo verify.
6. Выполнить rollback и подтвердить состояние.
7. Смоделировать ошибку записи receipt и получить `partial_success`.
8. Убедиться, что токены, SSH-пароль, sudo-пароль и тестовый секрет отсутствуют в выводах и receipts.
9. Повторить сценарий с двумя именованными сессиями без смешения host и target.
10. Проверить выполнение скрипта ограниченного размера без интерактивного stdin.

## Операционный вывод до реализации

Допустим общий `safe exec-risky` вокруг `ssh_relay sudo-exec --risky`, если явно заданы target, expected state, rollback, verify и удалённый receipt.

Команды с секретами нельзя передавать через `--risky`, пока удалённый receipt сохраняет полную команду. Сложные inline JSON и verify-команды в PowerShell следует заменять файлами.

Этот документ является отчётом и планом. Он не подтверждает реализацию перечисленных доработок в коде.
