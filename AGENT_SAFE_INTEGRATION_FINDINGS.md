# Findings интеграции ssh_relay с agent-safe

Дата исходного наблюдения: 2026-07-23.
Дата актуализации: 2026-07-31.

Документ сопоставляет исходные ограничения `ssh_relay 0.5.1` с фактическим состоянием версии `0.6.0` и оставшимися задачами адаптера `agent-safe`.

Android и Termux в исследовании не проверялись.

## Контекст

Практическая интеграция выполнялась через именованные relay-сессии при настройке SSH-доступа на удалённых Linux/VPS. Для изменения root-owned файлов использовался `sudo-exec --risky`.

Исходная задача выявила недостатки машинного результата, удалённого receipt, связи транзакций и Windows quoting. Эти наблюдения стали основанием для:

- [`ssh_relay#2`](https://github.com/dilukhin/ssh_relay/issues/2);
- [`agent-safe#4`](https://github.com/dilukhin/agent-safe/issues/4);
- машинного контракта версии 1.

## Сводка состояния

| ID | Исходный finding | Состояние после 0.6.0 | Что реализовано в ssh_relay | Что осталось |
|---|---|---|---|---|
| AS-1 | Специализированный адаптер не поддерживает `sudo-exec` | **Не решено на стороне agent-safe** | Relay имеет отдельный `sudo-exec` и тот же JSON-контракт, что `exec`. | Адаптер должен явно выбирать `exec` или `sudo-exec` и не оборачивать relay универсальным shell-вызовом. |
| AS-2 | Локальный и удалённый receipts не связаны | **Частично решено** | Relay принимает внешний `transaction_id`, создаёт `receipt_id`, возвращает receipt hash. | `agent-safe` должен сохранить remote ID/hash в локальном receipt и сопоставить оба уровня. |
| AS-3 | Составные команды классифицируются как unknown | **Не решено полностью** | Relay различает фактический runtime outcome, но не классифицирует смысл shell-команды. | Классификация риска, expected state, verify и rollback остаются в `agent-safe`; для сложных операций нужен ограниченный script-контракт. |
| AS-4 | PowerShell quoting ненадёжен | **Не решено** | Ограничение документировано; JSON-протокол не исправляет локальный разбор argv. | Добавить `--command-file`/`--command-stdin` либо script-команды; адаптеру использовать файловые параметры. |
| AS-5 | Перед изменением требуется discovery | **Частично решено операционно** | `status` и короткий `exec "hostname && whoami && pwd"` доступны. | Безопасный `inspect --json` не реализован; адаптер должен выполнять read-only discovery до risky. |
| AS-6 | Receipt сохраняет полную команду | **Исправлено** | Новый receipt хранит `command_hash`, target и описание, но не текст команды. | Проверить на реальном risky-сценарии отсутствие тестового секрета и полной команды. |
| AS-7 | Возможен частичный успех | **Исправлено в relay** | Есть `command_status`, `receipt_status`, `partial_success`, коды `12` и `13`. | `agent-safe` должен блокировать дальнейшие risky-операции и запускать verify/rollback по своей политике. |
| AS-8 | Целостность журнала не контролируется | **Реализован минимальный контроль** | Есть `receipt_hash`, `previous_receipt_hash`, self-hash preflight и legacy anchor. | Hash-цепочка не является подписью; требуется доверенный каталог и расширенная реальная проверка. |

## Что подтверждено практикой до 0.6.0

- `status --name` подтверждает доступность именованной сессии;
- `exec --name "hostname && whoami && pwd"` позволяет определить хост и рабочий контекст;
- `sudo-exec --risky` выполняет изменение и может вести удалённый журнал;
- stdout, stderr и exit code пригодны для внешней проверки;
- отдельный read-only verify позволяет проверить содержимое, owner и mode;
- последовательная обработка узлов не должна переводить остальные сессии в неопределённое состояние при сбое одного хоста.

## Что добавлено в ssh_relay 0.6.0

### Общий transaction ID

Адаптер может передать заранее созданный идентификатор:

```text
--transaction-id agent-safe:tx-001
```

Relay возвращает его в JSON и записывает в удалённый receipt.

Если ID не задан, relay генерирует UUIDv4, но такой режим хуже подходит для внешней транзакционной системы: при потере ответа вызывающая сторона может не знать созданный ID.

### Remote receipt ID и hash

Для успешной risky-команды создаются:

- `receipt_id`;
- `command_hash`;
- `receipt_hash`;
- `previous_receipt_hash`.

Эти значения возвращаются в машинном результате. `agent-safe` может сохранить их в локальном receipt.

### Раздельные исходы

Машинный режим различает:

```text
succeeded
command_failed
partial_success
not_started
unknown
```

Коды процесса:

| Код | Значение для адаптера |
|---:|---|
| `0` | операция успешна |
| `10` | основная команда достоверно не запускалась |
| `11` | получен ненулевой удалённый exit code |
| `12` | команда успешна, но receipt не подтверждён |
| `13` | результат основной команды неизвестен |

Коды `12` и `13` должны блокировать автоматическое продолжение транзакции.

### Безопасный receipt

Receipt 0.6.0 не содержит:

- текст команды;
- stdout;
- stderr;
- пароль;
- токен session-файла;
- приватный ключ.

Он содержит безопасные метаданные и hash точной пользовательской команды.

## Оставшиеся ограничения ssh_relay

### 1. Нет непрозрачного ввода команды

`exec` и `sudo-exec` по-прежнему принимают позиционный `remote_command`.

PowerShell, `cmd.exe` или POSIX shell могут обработать кавычки, `$()`, `%VAR%`, перенаправления и другие символы до запуска Python.

Требуется отдельная задача на:

```text
--command-file PATH
--command-stdin
```

или ограниченные `exec-script`/`sudo-exec-script`.

### 2. Нет `inspect --json`

Перед risky-операцией адаптер пока должен вручную выполнять короткий read-only discovery:

```text
status
hostname && whoami && pwd
проверка target
проверка sudo
```

Автоматизированный inspect должен быть безопасным и не раскрывать session token, пароли или приватный ключ.

### 3. Verify не является операцией relay

В 0.6.0 нет отдельного `--verify-command-file` и единого результата change+verify.

Это осознанное разделение ответственности:

- relay выполняет команду и возвращает достоверный транспортный результат;
- `agent-safe` определяет expected state, verify и rollback.

### 4. Идемпотентность не гарантируется

Повтор уже записанного `transaction_id` блокируется, но relay не доказывает, что незаписанная или unknown-команда безопасна для повторного запуска.

Решение принимает вызывающая сторона после read-only verify.

### 5. Hash-цепочка не является подписью

Пользователь, имеющий право переписать весь журнал, может пересчитать цепочку. Системный receipt должен находиться в доверенном каталоге.

## Ответственность ssh_relay

- поддерживать открытую SSH-сессию;
- выполнять короткие неинтерактивные команды;
- предоставлять отдельные `exec` и `sudo-exec`;
- возвращать машинный JSON-результат;
- различать command failure, partial success и unknown;
- записывать безопасный remote receipt;
- формировать IDs и hash;
- сохранять проверку host key;
- не раскрывать пароли, токены и ключи;
- не использовать прямой SSH из агента при активном relay.

## Ответственность agent-safe

- классификация риска;
- подтверждение пользователя;
- создание local transaction ID до запуска relay;
- выбор `exec` или `sudo-exec`;
- expected state;
- verify;
- rollback;
- локальный receipt;
- сопоставление local transaction с remote receipt;
- блокировка после `partial_success` и `unknown`;
- решение о повторном запуске;
- классификация составных shell-операций.

## Требования к адаптеру agent-safe

Адаптер должен запускать relay примерно так:

```text
ssh_relay.py sudo-exec \
  --name prod \
  --json \
  --risky \
  --transaction-id <local-id> \
  --change-target <safe-target> \
  --change-description <safe-description> \
  <command>
```

На Windows фактическое quoting следует минимизировать. Сложные параметры и будущие verify/rollback лучше передавать из файлов.

Адаптер должен:

1. ожидать ровно один JSON-объект;
2. не разбирать русскую строковую диагностику как основной контракт;
3. проверять локальный process exit code;
4. сохранять точный `command_exit_code`;
5. сохранять `receipt_id` и `receipt_hash`;
6. после `12` и `13` переходить в recovery/verify;
7. не повторять risky-команду автоматически;
8. не использовать прямой `ssh` при активной relay-сессии.

## Совместный интеграционный тест

### Подготовка

- запустить daemon с `--enable-sudo`;
- убедиться, что daemon действительно использует код 0.6.0;
- выполнить `status`;
- выполнить `hostname && whoami && pwd`;
- создать отдельный тестовый receipt path;
- выбрать безопасный тестовый target.

### Сценарии

1. Через `agent-safe` создать root-owned тестовый файл командой `sudo-exec --json --risky`.
2. Подтвердить локальный и удалённый receipts.
3. Проверить общий `transaction_id`.
4. Проверить remote `receipt_id`, `command_hash` и `receipt_hash`.
5. Выполнить sudo verify owner/mode/content.
6. Выполнить rollback и подтвердить исходное состояние.
7. Смоделировать command failure.
8. Смоделировать receipt failure после успешной команды.
9. Смоделировать unknown основной команды.
10. Убедиться, что последующие risky-операции блокируются после неопределённого результата.
11. Проверить отсутствие токенов, SSH-пароля, sudo-пароля и тестового секрета.
12. Повторить безопасный сценарий с двумя именованными сессиями без смешения host и target.

## Текущее решение по Issue #2

Реализация P0 в `ssh_relay` в основном завершена и подтверждена локальными тестами и кратким реальным SSH smoke-тестом.

Issue #2 пока следует оставлять открытым до расширенной реальной проверки:

- записи risky JSONL на Linux;
- `sudo-exec --json --risky`;
- receipt failure и unknown;
- сетевого разрыва или timeout после запуска;
- двух именованных сессий;
- совместимости с адаптером `agent-safe`.
