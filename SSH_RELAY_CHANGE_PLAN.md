# План изменений ssh_relay для интеграции с agent-safe

## Назначение

План определяет изменения только в проекте `ssh_relay`. Доработки адаптера, классификации риска, expected state, rollback и verify выполняются отдельно в `agent-safe`.

Связанные материалы:

- findings: [`AGENT_SAFE_INTEGRATION_FINDINGS.md`](AGENT_SAFE_INTEGRATION_FINDINGS.md);
- задача `ssh_relay`: [#2](https://github.com/dilukhin/ssh_relay/issues/2);
- задача `agent-safe`: [dilukhin/agent-safe#4](https://github.com/dilukhin/agent-safe/issues/4).

Код в рамках подготовки этого плана не изменяется.

## Исходное состояние

Текущая версия кода: `0.5.1`.

Уже поддерживаются:

- именованные сессии;
- `exec` и `sudo-exec`;
- `--risky` и удалённый JSONL receipt;
- `download` и `upload`;
- `status`, `list`, `stop`;
- проверка host key через `known_hosts`;
- ограничения времени и объёма вывода.

Текущие ограничения risky-протокола:

- CLI не выдаёт полный машинный результат операции;
- receipt сохраняет полную команду;
- отсутствуют `transaction_id` и `receipt_id`;
- ошибка записи receipt после успешной команды представляется общей ошибкой;
- целостность последовательности receipt-записей не контролируется.

## Целевая версия

Новые параметры, машинный формат и новые команды являются расширением возможностей CLI. Планируемая версия после полной реализации: `0.6.0`.

Версию следует менять только одновременно с фактической реализацией и обновлением README.

## Этап 1. Зафиксировать машинный контракт risky-операции

Приоритет: P0.

До изменения кода необходимо утвердить JSON-схему результата для `exec --risky` и `sudo-exec --risky`.

Минимальные поля:

```json
{
  "schema_version": 1,
  "session": "prod",
  "remote_target": "donpedro@198.51.100.42:22",
  "command_status": "succeeded",
  "command_exit_code": 0,
  "receipt_status": "written",
  "partial_success": false,
  "receipt_path": "/var/lib/agent-safe/changes.jsonl",
  "receipt_id": "...",
  "receipt_hash": "...",
  "transaction_id": "...",
  "sudo": true,
  "timestamp_utc": "..."
}
```

Требуется определить:

- отдельный параметр включения JSON-вывода;
- канал вывода JSON и правила совместимости с stdout/stderr удалённой команды;
- допустимые значения `command_status` и `receipt_status`;
- поведение при ошибке relay до запуска удалённой команды;
- поведение при ошибке записи receipt после успешной команды;
- правила возврата process exit code для partial success;
- максимальную длину и формат передаваемого `transaction_id`.

Рекомендуемый принцип: машинный JSON не должен смешиваться с stdout удалённой команды. Возможные варианты необходимо сравнить до кодирования: отдельный файл результата, отдельный дескриптор либо режим, в котором stdout целиком занят JSON, а удалённые stdout/stderr включены в структуру с ограничением размера.

## Этап 2. Безопасный формат удалённого receipt

Приоритет: P0.

Receipt по умолчанию не должен содержать полную команду.

Обязательные данные:

- `schema_version`;
- `timestamp_utc`;
- `tool` и версия relay;
- имя сессии;
- устойчивый идентификатор хоста;
- безопасное описание действия;
- target;
- режим sudo;
- `command_hash` или `script_hash`;
- command exit code;
- `transaction_id`;
- `receipt_id`;
- `previous_receipt_hash`;
- `receipt_hash`.

До реализации необходимо определить:

- алгоритм hash;
- каноническое JSON-представление для вычисления `receipt_hash`;
- получение предыдущего hash без гонок;
- поведение при отсутствующем или повреждённом журнале;
- допустимость явного режима сохранения полной команды;
- правила редактирования чувствительных полей.

Полную команду нельзя пытаться безопасно очищать эвристикой и затем считать результат гарантированно безопасным. Безопасный режим должен строиться на явном описании и hash.

## Этап 3. Partial success

Приоритет: P0.

Нужно различать следующие результаты:

1. команда не запускалась;
2. команда запущена и завершилась ошибкой;
3. команда успешна, receipt записан;
4. команда успешна, receipt не записан;
5. команда успешна, но результат записи receipt неизвестен из-за разрыва соединения.

Состояния 4 и 5 должны быть явно машинно различимы. Нельзя сообщать, что команда не выполнена, если удалённое состояние уже изменено.

До реализации необходимо определить:

- process exit code для каждого состояния;
- текстовую диагностику для оператора;
- наличие данных, достаточных для verify и rollback;
- поведение при повторном запуске с тем же `transaction_id`;
- защиту от создания дублирующего receipt.

## Этап 4. inspect --json

Приоритет: P1.

Команда должна возвращать безопасный контекст активной сессии:

- session name;
- host, port и SSH user;
- hostname удалённого узла;
- remote cwd;
- режим sudo;
- версию relay;
- fingerprint host key либо другой устойчивый идентификатор узла.

Команда не должна выводить:

- session token;
- SSH-пароль;
- sudo-пароль;
- приватный ключ;
- содержимое session-файла.

До реализации нужно проверить, какие данные уже доступны локально, а какие требуют короткой удалённой команды.

## Этап 5. exec-script и sudo-exec-script

Приоритет: P1.

Назначение: выполнить проверенный короткий скрипт без сложного quoting командной строки.

Ограничения:

- только обычный локальный файл;
- отдельный небольшой лимит размера;
- содержимое читает CLI-процесс и передаёт daemon;
- hash вычисляется по переданным байтам;
- shell выбирается явно из ограниченного списка;
- интерактивный stdin закрыт;
- действуют существующие command timeout и output limit;
- каталоги и рекурсивная передача не поддерживаются;
- временный файл на сервере либо не создаётся, либо удаляется гарантированно и документированно.

До реализации необходимо выбрать способ передачи содержимого: stdin удалённого shell, временный файл с последующим удалением либо другой ограниченный протокол.

## Этап 6. Проверки

### Без SSH-сервера

- `py -m py_compile ssh_relay.py`;
- проверка `--version` и всего `--help`;
- модульные проверки формирования канонического receipt;
- тестовые векторы hash;
- проверка JSON-схемы каждого результата;
- проверка отсутствия секретов в результатах и receipts;
- проверка лимитов `transaction_id`, описания и script content.

### С тестовым сервером

Перед проверкой изменённого daemon его необходимо перезапустить.

Проверить раздельно:

- `exec --risky`;
- `sudo-exec --risky`;
- command failure;
- receipt failure после успешной команды;
- разрыв соединения после выполнения команды;
- повторный transaction ID;
- повреждённую последнюю строку receipt;
- `inspect --json`;
- выполнение скрипта;
- две именованные сессии на разных хостах;
- stdout, stderr и exit code;
- отсутствие токенов, паролей и тестового секрета.

### Windows

Проверки документируются отдельно для PowerShell и `cmd.exe`.

- PowerShell: код завершения проверяется через `$LASTEXITCODE`;
- `cmd.exe`: код проверяется в той же строке через `%ERRORLEVEL%` либо delayed expansion;
- в Far Manager нельзя проверять `%ERRORLEVEL%` отдельной следующей командой.

## Разделение ответственности

### ssh_relay

- удалённое выполнение;
- JSON-контракт результата;
- remote receipt;
- идентификаторы и hash;
- partial success;
- безопасный inspect;
- ограниченное выполнение скриптов.

### agent-safe

- классификация риска;
- подтверждение пользователя;
- expected state;
- rollback;
- verify;
- локальный журнал транзакций;
- блокировка после неожиданного результата;
- сопоставление local transaction с remote receipt.

`ssh_relay` не должен принимать на себя политику классификации риска `agent-safe`. `agent-safe` не должен самостоятельно воспроизводить SSH-протокол и обходить relay.

## Порядок реализации

1. Утвердить JSON-контракт и process exit codes.
2. Утвердить безопасную схему receipt и hash.
3. Реализовать P0 в `ssh_relay`.
4. Проверить P0 вручную и без сервера, и на тестовом сервере.
5. Реализовать поддержку контракта в `agent-safe`.
6. Выполнить совместный интеграционный тест.
7. Отдельно решить необходимость `inspect` и script-команд.

Переходить к кодированию следует только после согласования этапов 1–3.
